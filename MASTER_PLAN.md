# Introduction
The goal of this project is to characterize the NVIDIA RT core which is expressed as TTU "Tree Traversal Unit" instructions at the SASS level. The RTX 6000 Ada (SM89) will be the primary target hardware for this effort. Every microbenchmark and BITTU test will be repeated on an RTX 4070 Ti (SM89, a smaller chip of the same generation) and on a GPU from a different generation (TBD). This project will consist of a suite of microbenchmarks designed to characterize a performance model of the RT core and a binary instrumentation tool to measure and validate performance characteristics.

The RAGRT project showed us that mapping a problem onto the RT cores can make the performance slower despite expectations. Currently the only way to find this out is to build the entire mapping then measure it. Search dominating runtime, data being natively 3D, scenes being sufficiently large, rays having few hits, and data being irregular enough that grids lose are the expected conditions which would justify RT speedup but these conditions are largely qualitative and not enough.

This project aims to replace the existing approach of reasoning about mapping performance with a performance model of the RT core based on actual measurements of the hardware, with the tooling needed to evaluate RT core performance in real programs.

# EoSS
EoSS is a framework which runs arbitrary SASS instructions on real GPUs bypassing the NVIDIA assembler. EoSS uses the readable ISA description "Rosetta String" from NVIDIA's tooling and parses it into a per architecture JSON. This includes every instruction class along with its opcode, operand bit fields, modifiers, scheduling properties and the constraint expressions that make an encoding legal. From this EoSS encodes using a constraint aware generator which builds valid 128 bit encodings for any class which includes the control bits, stall count, yield, scoreboard read, write, and wait masks. A pure Python CUDA ELF parser finds the .text sections in a compiled binary, locates the kernel code by byte anchors and patches instructions in place. Then, an nvcc compiled kernel with thousands of patchable "slots" bracketed by clock reads has its instructions patched by EoSS. EoSS then runs the binary and reads back the per slot timings. Finally EoSS provides a CLI tool and a SASS editor for testing and experimentation.

## EoSS Insights
EoSS discovered eight TTU instruction classes: TTUOPEN, TTUMACROFUSE, TTUST, TTUGO, TTULD, TTULD.CLOSE, TTUCLOSE, and TTUCCTL. 

TTU instructions are hidden by cuobjdump and nvdisasm and unreachable to PTX as only OptiX's JIT compiler emits them. The EoSS paper runs them from a plain CUDA compute kernel. The standard TTU sequence always starts with TTUOPEN then TTUMACROFUSE N and then N fused instructions including TTUST, TTUGO, TTULD, and TTULD.CLOSE. 

If the fuse count is not equal to the correct number of fused instructions then the GPU hangs. Sessions are per warp and are tracked using SR_TTU_TICKET_INFO (SR133). A second TTUOPEN on an open session faults. Omitting TTULD.CLOSE permanently hangs the GPU. The driver closes open sessions during preemption.

The BVH must live in the low 4GB of the address space as some pointers are 32 bit. Child pointers are absolute addresses. (Not true for OptiX's own GAS on SM89: ours sat at 0x7fc0ede00a00 and traced fine. See notes/protocol.md; BVH_6 tests the limit.)

Measured on SM120, traversal latency is about 1,600 cycles at depth 1, then 2,100, 2,900, and 4,400 cycles at depths 2, 3, and 4, and nearly flat in triangle count. Per instruction issue costs are TTUOPEN 6, TTUMACROFUSE 6, TTUST 9, TTUGO 5, TTULD 5, TTULD.CLOSE 62, and TTUCCTL at 10 cycles. Validation is done via the Nsight Compute counter rtcore__rays.sum. (The installed ncu versions list no rtcore__ metric for AD102; checked 2026-11-09.)

## EoSS missing info
The README refers to `TTU/`, `Contention/`, `OSIRIS/`, `VisualModifier/` and `Unintentional/` directories, but they are not present. We need BVH builder and encoder, and the compute mode ray tracer ("Ecce Mono"), the OptiX JIT cubin dump, the in memory patch tool, and the TTU timing harness.

TTU encodings are packaged only for SM120 and our GPU is SM89. The SM89 ISA JSON has all eight TTU classes. TTUST's second source and TTULD's second destination (bits 71:64) are ordinary registers on both architectures: the field is named Ra_URc on SM120 and Rc on SM89, but its operand type is Register on both, and both use even aligned 64 bit register pairs (IDEST_SIZE 64; TTULD requires even Rd and Rd2). (Corrected 2026-11-10, from Cesar; an earlier version said SM120 used a uniform register.) The SM89 encodings were still generated with the EoSS encoder, and 9 of 10 canonical instructions are byte identical to SM120.

The README lists CUDA 13.0+ and ncu with counter permissions as prerequisites while docs/results.md validated SM89 using CUDA 12.8. On triton we installed CUDA 12.8 in `~/opt/cuda-12.8` (the driver supports up to 13.0), and ncu counters are open to non admins.

# What we want to learn about the hardware
Each question is tagged with what its answer feeds: the performance model (PM), the binary instrumentation tool (BIT), an optimization opportunity (OPT), or the DSL's mapping decision (DSL).

## A: Interface and protocol
1. What every TTUST offset carries - origin, direction, tmin, tmax, root pointer, ray flags, cull mask, instance and SBT fields, and what is required - BIT OPT
2. What every TTULD offset returns - hit/miss, primitive ID, t, barycentrics, instance ID, geometry index, and any other information. What the Pu predicate means - BIT PM
3. Fusion rules - allowed numbers and orders of TTUST/TTULD, minimum legal group, and maximum count - BIT
4. Lane semantics - One ray per thread? What inactive or diverged lanes do, and if the cost is per ray or per warp - PM OPT
5. Session semantics - Can one session issue multiple TTUGOs? Can a warp keep several queries in flight? What does /DUAL do? SR133 values - PM OPT
6. Ray flags - closest hit vs terminate on first hit, culling, opaque handling, and if the TTU can return multiple hits per ray - PM DSL
7. TTUCCTL semantics - what it invalidates and what that costs - PM

## B: BVH format and scene building
1. Node layout - box node header, branching width, box quantization or compression, child pointer encoding, leaf and triangle block layout - BIT OPT
   - David's early tests suggest a 12 wide layout, leaves stored as one contiguous primitive list that leaf boxes point into by offset, and no duplicated triangles. To verify in BVH_1.
2. Primitive types besides triangles - custom AABB primitives, how control returns to SM for intersection, and any other native primitives - PM DSL
3. Two level scenes - instances, TLAS/BLAS, transforms - OPT
4. Starting traversal at an internal node - is it allowed, is the result identical to a root start for rays within the subtree, what happens when a ray leaves the subtree's box, and how much latency is saved per skipped level - OPT
5. Address and alignment constraints - low 4GB, node alignment, and maximum scene size - BIT

## C: Latency of single traversal
1. Cost per visited node and per tree level and if it depends on internal branching - PM
2. Cost per primitive test - triangle vs box vs custom primitive round trip to the SM - PM DSL
3. Cost per returned hit and when a ray reports more than one - PM DSL
4. Fixed overhead per traversal - open, store, go, load, and close - PM
5. Cold vs warm - first touch vs repeated traversal of the same nodes - PM

## D: Throughput and concurrency
1. How many traversals one RT core keeps in flight and the throughput curve vs warps per SM - PM OPT
2. Ray coherence - how throughput changes coherent vs incoherent - PM OPT
3. Overlap with SM work - can a warp or other warps perform useful work between TTUGO and the result? Does TTU contend with LSU/L1? - PM DSL
4. Scaling across SMs - Is there a shared bottleneck of L2 and memory - PM
5. RT cores per TPC - NVIDIA lists one RT core per SM (142 on the RTX 6000 Ada), but Cesar believes there is physically one per TPC, shared by its two SMs. (Measured: the unit is shared per TPC; it is the limit for long or memory heavy queries, while for short queries the SM side costs dominate and both SMs contribute, F105.) If true, C_inflight and peak throughput halve per SM and TPC placement matters - PM OPT

## E: TTU memory hierarchy 
1. Which path node fetch take (L1, dedicated TTU cache, L2) and if SM memory traffic interferes - PM
2. Capacity and behavior of any TTU node cache - PM OPT
3. Bytes fetched per node and per traversal - behavior when BVH exceeds L2 (96MB on the RTX 6000 Ada) - PM DSL
4. Locality - does grouping rays that traverse the same subtree measurably reduce latency or DRAM traffic? - OPT
5. TPC sharing - two SMs form a TPC; when node data misses or is evicted from the RT core's cache, does it land in only its own SM's L1, in both SMs' L1, or neither? (raised by David) - PM OPT

## F: Traversal behavior
1. Traversal order (nearest child first? fixed order?) and early termination as tmax shrinks - PM OPT
2. Stack depth limits, short stack restarts, costs of very deep trees - PM
3. Sensitivity to overlapping and degenerate boxes - PM DSL
4. Numerical behavior - conservative box tests, watertight triangle tests, and precision of t - BIT

## G: Architecture generality
1. Which findings hold on the RTX 4070 Ti (SM89, smaller L2 and fewer SMs) and on a GPU from another generation, as well as the RTX 6000 Ada - PM DSL

# Potential performance model
This is a potential performance model which may significantly change after microbenchmarking the RT cores.

**Latency of one traversal**

T_ray ≈ t_fixed + Σ over visited nodes of t_node(cache state) + Σ over tested primitives of t_prim(type) + n_hits · t_hit

- `t_fixed`: open, stores, go, loads, close (Latency_1).
- `t_node`: per node cost, split by where the node came from (Latency_2, Latency_3, Memory_2).
- `t_prim`: per primitive test, triangle vs custom (Latency_4, BVH_3).
- `t_hit`: cost per reported hit (Latency_5).

**Throughput of one RT core**

X_rt ≈ min( C_inflight / T_ray , BW_nodes / bytes_per_ray , issue rate )

- `C_inflight`: queries in flight per RT core (Throughput_1, Throughput_2).
- `bytes_per_ray`: node and primitive bytes fetched (Memory_3).

**Whole kernel (the Amdahl part)**

T_kernel ≈ f(T_traversal, T_SM_work, overlap)

where overlap comes from Throughput_4. The DSL compares this against the cost of the best CUDA or CPU alternative for the same query.

# Microbenchmark suite
## Microbenchmark methodology
- **Harness.** Each benchmark is a compute kernel compiled with nvcc in which placeholder instructions are patched into TTU sequences with EoSS (`BinaryPatcher` + our SM89 TTU encodings). Timing uses `CS2R SR_CLOCKLO` reads; completion latency uses a scoreboard wait on the `TTULD` result, as in EoSS's `completion` mode.
- **Scenes** come from our own BVH builder (BVH_2) so that depth, width, leaf size, overlap and footprint are controlled exactly. Each scene has a CPU reference result.
- **Correctness first.** Every timing run also checks every returned result against the CPU reference. A run with wrong results is discarded.
- **Repetitions.** Warmup runs, then at least 30 repetitions; report the median and the 5th/95th percentiles. Fixed clocks where possible (`nvidia-smi --lock-gpu-clocks`), GPU otherwise idle.
- **Ground truth counters.** Cross check with Nsight Compute RT and memory counters (`rtcore__rays.sum` and the L1/L2/DRAM metrics) whenever permissions allow.
- **Records.** Each run writes a CSV plus a JSON metadata file (GPU, driver, clocks, git commit, scene parameters).
- **Safety.** Every run under a hard timeout, on a GPU nobody else is using.

# Binary instrumentation tool

Working name: **BITTU**

## Intended use
While the microbenchmarks can measure the TTU in isolation, a binary instrumentation tool is needed to measure performance inside real programs to determine behavior such as how many traversals they issue, how long each takes, how many hits each ray gets, how much of the kernel's time is traversal, and which rays and subtrees it touches. This information will be crucial in developing and validating a performance model.

## What it should do

| Capability                                                                                                                                                                                                                  | How                                                                                                                             |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Find TTU code** in any cubin, including JIT dumps: list sessions and fused groups, their shapes, and which TTU offsets they read and write.                                                                               | Decode with the EoSS ISA JSON (the standard disassemblers hide TTU instructions).                                               |
| **Count** traversals per warp, per kernel, per SM.                                                                                                                                                                          | Probe before each `TTUOPEN`.                                                                                                    |
| **Time** each traversal end to end.                                                                                                                                                                                         | Clock before `TTUOPEN`, clock after the first instruction that consumes a `TTULD` result. Subtract a calibrated probe overhead. |
| **Capture rays**: the values stored by each `TTUST` (origin, direction, tmin/tmax, flags), sampled.                                                                                                                         | Read the source registers before the fused group (they already hold the values).                                                |
| **Capture results**: hit, primitive, t, per ray.                                                                                                                                                                            | Read the `TTULD` destination registers after the group.                                                                         |
| **Derived metrics**: hits per ray, active lanes per traversal, fraction of kernel time spent waiting on traversal, traversals over time per SM.                                                                             | Host side analysis of the above.                                                                                                |
| **Replay**: run captured rays offline through a software traverser over the dumped BVH to recover nodes visited, depth reached, overlap, and which subtrees each ray touched (the hardware probably does not report these). | Needs the decoded node format (BVH_1). Validate replay against measured latency.                                                |
| **Hardware counters** per kernel as ground truth.                                                                                                                                                                           | CUPTI Profiling API or `ncu` (RT, L1, L2, DRAM metrics).                                                                        |

Modes: 
- **count** (cheapest)
- **sample** (1 in N warps or traversals)
- **trace** (everything, for small runs).

## Tool constraints

1. **Never insert code inside a fused group.** `TTUMACROFUSE(n)` fuses the next n instructions, so any inserted instruction breaks the group and hangs the GPU. This also rules out instrumenting `TTUMACROFUSE` itself, because trampoline style tools (NVBit included) relocate the instrumented instruction into a stub and follow it with a branch, which would be counted as fused. **Legal probe points: before `TTUOPEN`, and after the last instruction of the group.** Interface_3 tests whether raising the count to N+1 lets a single inline instruction sit inside the group; even if it does, an NVBit probe is far more than one instruction, and timing after the group already captures the full latency because the first consumer of a `TTULD` result is what waits.
2. **Do not disturb result scoreboards.** `TTULD` writes through a variable latency scoreboard; probes that read its destination registers must wait on it (place them after the original consumer, or add the matching wait).
3. **Respect session state.** Never issue anything that could open a second session or skip `TTULD.CLOSE`.
4. **Account for overhead.** Probes add cycles. Every timing mode needs a calibration run with empty probes, and results should be reported with and without the tool.

## Building on prior work
NVBit (NVIDIA Labs, MICRO 2019) is a dynamic binary instrumentation framework for NVIDIA GPUs, similar in spirit to Pin for CPUs. When a kernel loads, an NVBit tool can inspect every SASS instruction and inject calls to its own device functions before or after any of them, with access to register values. This lets it count, time and capture data inside unmodified binaries without recompiling them. Its core is closed source, so if its decoder does not understand TTU instructions we cannot fix it, and it is unknown whether it sees the kernels OptiX's JIT compiler produces. CUPTI is NVIDIA's profiling interface. It provides hardware counters per kernel (on SM120 this includes RT core counters such as `rtcore__rays.sum`; ncu lists none for AD102, see Findings; plus L1, L2 and DRAM metrics) and activity traces. Its SASS Metrics API also patches SASS, but only to collect NVIDIA's predefined metrics: it cannot run custom probes or read registers. Its PC sampling and Metric APIs do not support OptiX applications, while its Profiling API does.

BITTU will be an NVBit tool. When a module loads, BITTU decodes each function's instructions with a TTU decoder generated from the EoSS SM89 ISA JSON (the TTU opcode masks and field layouts exported as a C++ header), since NVBit itself may not recognize TTU instructions; if NVBit's SASS text hides them, BITTU reads the raw code bytes instead. From this it finds every session and fused group, then inserts probes only at legal points (before `TTUOPEN` and after the group) to count traversals, time them and capture ray and result registers into device buffers that the host collects. CUPTI's Profiling API (or `ncu`) runs alongside to collect per kernel counters as ground truth for BITTU's counts. EoSS's static patcher builds the microbenchmarks and gives kernels with known answers to validate BITTU against. Before committing to NVBit, four quick tests decide it: whether it lists TTU instructions correctly, whether empty probes around a fused group run without hanging, whether a probe reads the `TTUST` source registers correctly, and whether OptiX's JIT kernels are visible at all. If the last one fails, OptiX programs fall back to clock reads around `optixTrace` in our own raygen code.

# Findings
Short dated list of what we have learned, in words only. Details and evidence are in the private notes. Add each new finding here with a date. Numbered in the order found; every entry is dated.

1. **2026-11-09, TTULD.CLOSE is bit 74 on SM89.** Read from real SM89 OptiX code (and from a Turing warmup kernel inside the OptiX library). Bit 72, which Cesar's SM120 file gives as the close bit, is the `.DUAL` flag of TTUOPEN; no TTULD we have seen sets it.
2. **2026-11-09, fuse count rule.** TTUMACROFUSE N equals the number of TTU instruction slots after it, including predicated ones that do not execute (OptiX's main traversal group has N = 17 with 6 predicated stores). The CLOSE is never predicated. In every group we have, the N instructions are contiguous TTU instructions, so we cannot yet tell whether non TTU instructions inside a group would count (Interface_3).
3. **2026-11-09, SM89 traversal sequence.** OptiX's ray traversal on Ada is one fused group: TTUOPEN.DUAL, TTUMACROFUSE 17, ten TTUSTs (offsets 0xC0, 0xD0, 0x200 or 0x100, 0x180, 0x190, 0, 0x40, 0x50, 0x80), TTUGO, six TTULDs (0x300, 0x310, 0x320, 0x380, 0x3C0, 0x3D0, the last one closing). Stores set a read scoreboard and loads a write scoreboard, unlike Cesar's sequence. The smallest legal sequence NVIDIA ships is OPEN, FUSE 2, GO, LD.CLOSE with no store.
4. **2026-11-09, store sources.** 0x40 and 0x50 carry origin plus tmin and direction plus tmax; 0xC0 and 0xD0 repeat them. The other stores are built from ray flags, the visibility mask, ray time and one OptiX launch constant. Raygen packs flags and mask into one word (flags << 16, mask << 8, then 1).
5. **2026-11-09, OptiX always adds an instance level.** Even for a single GAS, store 0x100 points to a small instance node that OptiX builds itself (identity 3x4 transform), sitting next to its program dispatch table; the GAS root goes in store 0x180. So the RT core starts at an instance level even with one object. Setup_3 points 0x100 at OptiX's own node in the same process; building our own instance node is part of BVH_1. This is also why Cesar's 4 store sequence has no root pointer on SM89.
6. **2026-11-09, shadow rays skip stores (future latency test).** The predicated stores depend on one test: they are skipped only when a ray has both TERMINATE_ON_FIRST_HIT and DISABLE_CLOSESTHIT (the usual shadow ray). Shadow style any hit queries send less to the RT core and may be cheaper; a Phase 3 latency benchmark should compare them with closest hit rays. Relevant to the model's "few hits per ray" question.
7. **2026-11-09, some store words come from registers nothing initializes, and registers are not cleared at launch.** Half of 0x180 and all of 0x190 come from registers that OptiX never writes before the traversal in our pipeline. A plain CUDA test (fill the whole register file, then read every register at the start of the next kernel) found no zeroing: registers start with leftover or unpredictable values, not 0. So OptiX sends arbitrary data in those words and traversal is still correct, which suggests the RT core ignores them in this mode. Interface_1 should test that directly.
8. **2026-11-09, the BVH does not need the low 4 GB.** OptiX's GAS on SM89 sat near 128 TiB and traced correctly; pointers are full 64 bit addresses in 64 or 128 byte units. The paper's low 4 GB rule may hold for Cesar's format or SM120; BVH_6 tests it.
9. **2026-11-09, first GAS (one triangle).** 2304 bytes: a header with section offsets, a root node with 12 child slots (fits David's 12 wide result), what looks like a compressed triangle leaf, and the GAS's own GPU address inside it (not position independent, so it cannot be copied between processes).
10. **2026-11-09, OPEN: a second copy of the traversal code at fnaddr minus 0x1C00.** 14 TTU instructions with no OPEN or FUSE before them. It is part of a larger copy of the traversal function with raygen code written over its middle, so it is most likely stale code left in memory, but it could be a resume path entered by an indirect branch. Not settled.
11. **2026-11-09, no ray counter on AD102.** `rtcore__rays.sum` does not exist for AD102 in ncu 2024.1 or 2025.1, and no metric has a ray related name. Two stall metrics have a "non RTCORE" part, so their difference shows RT core stalls, not rays. Correctness checks use a CPU reference and an in process OptiX launch.
12. **2026-11-09, NVIDIA hides OptiX traversal from every official tool.** Hooking the driver's code loaders saw nothing (OptiX loads code through a private interface); the OptiX disk cache holds only user programs (traversal is added at pipeline link); CUPTI and ncu list only user functions; cuda-gdb is blocked by the server's ptrace setting. Reading code from GPU memory with plain loads worked. This is the gap BITTU is meant to fill.
13. **2026-11-09, possible EoSS issue: SM89 JSON lacks SEL with an immediate.** Opcode 0x807 (SEL Rd, Ra, imm, Pp) appears 20 times in OptiX's traversal code but is not in the SM89 ISA JSON (the register and constant forms are). The Decoder also prints constant operands without bank and offset and drops some immediates. Worth reporting upstream once checked against SM120.
14. **2026-11-09, first TTU traversal from a plain CUDA kernel on SM89 (Setup_3).** One warp ran NVIDIA's own fused traversal group, unchanged, with registers we filled, against an OptiX built one triangle GAS and OptiX's instance node in the same process. No hang or fault. Hit and miss rays give clearly different results, the same in all 32 lanes. On a hit the loads return the barycentrics, the hit distance, the address of the hit triangle block and the hit instance; on a miss those words are all ones or zero. Two hit values (t and one barycentric) come back with the sign bit set, not yet explained.
15. **2026-11-09, the RT core ignores the uninitialized store words here.** Random data instead of zeros in those words gives identical traversal results.
16. **2026-11-09, what the main TTULDs return (one triangle).** A hit returns the hit distance negated (sign bit always set), the two barycentrics exactly to the float bit, with the sign of the first one marking which face was hit (set for a back face hit by OptiX's convention), a hit flag, the address of the hit triangle block, and the hit instance. A miss returns all ones in the distance and barycentric words and zeros elsewhere. One word is always negative zero on a hit and is still unexplained.
17. **2026-11-09, first measured traversal latency on SM89.** One warp, one ray per lane, one triangle under OptiX's instance level, BVH already in cache: about 1,640 cycles from TTUOPEN to the last result (median of 30, spread about 10 cycles, all lanes equal), about 1,560 after subtracting the cost of the clock reads and an empty group slot. EoSS reports about 1,600 cycles at depth 1 on SM120, so the two are in the same range, but the setups differ (architecture, BVH format, instance level, timing method), so this is not yet a like for like comparison.
18. **2026-11-09, face flag confirmed.** OptiX's own front face query agrees: the sign bit on the first barycentric is set exactly for back face hits.
19. **2026-11-09, primitive index and leaf slot.** One TTULD word carries the hit primitive index in its low bits (checked up to 10,368) under a 3 bit flag field whose value changes for large scenes (meaning unknown). The leaf address word also carries which triangle slot inside the leaf block was hit. The word we guessed might be the primitive index is always zero.
20. **2026-11-09, cold vs warm.** Reading 256 MB (more than the 96 MB L2) right before a timed launch raises one traversal of the one triangle scene from about 1,640 to about 2,630 cycles; an empty group slot is unaffected, so the cost is BVH data coming from DRAM.
21. **2026-11-09, GAS node format (first decode).** 128 byte internal nodes with 12 child slots; one slot field marks empty, internal and leaf children; internal children of a node are stored together and found from one offset field; a header word gives the node count, and walking the tree with these rules reaches exactly that count in all 33 dumps (1 to 30,000 triangles). Leaves hold several triangles.
22. **2026-11-09, latency vs depth.** One warp, with the BVH depth measured from the GAS dump each time: warm about 1,640 / 1,910 / 2,315 cycles at 1 / 2 / 3 internal levels (plus OptiX's instance level), about 2,640 for a scene whose ray is likely at level 4; cold about 2,650 / 3,230 / 3,890. Each level adds roughly 270 to 400 cycles warm and 600 to 750 cold. EoSS's SM120 numbers grow faster per level (about 1,600 to 4,400 over 4 levels); the setups differ, so this is a first comparison only.
23. **2026-11-09, Throughput_1 on one SM.** With 1, 2, 4, 8, 16 warps on one SM (one ray per lane, same ray, BVH warm), the RT core finishes 0.020, 0.032, 0.047, 0.068 and 0.085 rays per cycle, about 12 cycles per ray at 16 warps, while each warp's latency rises from about 1,640 to about 2,960 cycles. Warps reach the group at staggered times because of our setup code, so the 16 warp rate is a lower bound.
24. **2026-11-09, one SM throughput with aligned starts (coherent rays).** A blocking barrier plus a short gap lines up all warps within about 30 cycles (a warp issues a few instructions past a barrier before it stalls). The TTU group's register footprint caps one block at 20 warps per SM (96 registers per thread; the declared count must exceed the highest register used by at least 3). From 1 to 20 warps, with every lane tracing the same ray, throughput rises from 0.020 to 0.090 rays per cycle while per warp latency rises from about 1,640 to about 4,900 cycles; by Little's law about 14 warps (about 440 rays) are in flight at 20 warps. Warps finish at a steady 5.7 to 7.4 cycles per ray. Throughput is still rising at the ceiling, so the RT core is not saturated there; remapping the group to fewer registers would allow more warps.
25. **2026-11-09, truly warm traversal.** Tracing the same ray twice in one kernel and timing the second: about 780, 830 and 870 cycles at 1, 2 and 3 internal levels, so about 43 cycles per level when everything is cached, and about 740 cycles of fixed cost. A traversal that is warm only across kernel launches costs about 1,640 to 2,300 cycles.
26. **2026-11-09, memory latency and the per level cost.** A plain pointer chase on one SM gives L1 about 41 cycles, L2 about 292 to 298, DRAM about 616 to 654; L1 contents do not survive a kernel boundary. Each extra BVH level costs about one dependent access at the level where its node sits (about 43 in kernel = L1, 270 to 400 across launches = L2, 580 to 750 cold = DRAM), so the RT core's node fetches behave like loads through L1.
27. **2026-11-09, Throughput_8: SM pairs share a traversal resource.** With 20 warps on each running SM (coherent rays), two SMs 2k and 2k+1 running at the same time each drop to about 70% of their solo rate (pair total about 1.45 times one SM), while two SMs further apart (0 and 2, 2 and 4) each keep their full rate. This fits one RT core (or another shared path) per TPC, as EoSS claims; the pairing of SM numbers into TPCs is inferred from the block placement pattern and this result, not documented.
28. **2026-11-09, coherence (first test).** Giving every lane a different ray, to a different triangle and a different BVH path in a 144 triangle scene, changes neither throughput nor latency measurably (within about 3%) from 1 to 20 warps. The scene fits in L1 and all rays are parallel, so this shows that path divergence alone is free here; incoherence through a large memory footprint is not yet tested.
29. **2026-11-09, coherence matters once the BVH leaves L1.** With random ray origins and directions in a cloud of random triangles, each lane's ray takes its own path. For a 3 KB BVH, random rays are as fast as coherent ones. For BVHs of 654 KB, 6.5 MB and 195 MB (bigger than L1, up to twice L2), random rays get 4 to 6 times less throughput than rays shared by all lanes at 20 warps, and 2 to 3.5 times higher latency at 1 warp. With random rays, 20 warps can deliver less throughput than 8 (cache thrashing).
30. **2026-11-09, one TTU query is not always a whole ray.** In large scenes the last two loads of the group return values shaped like BVH node pointers, and in a few lanes the returned hit is real but not the closest one OptiX finds. This suggests the RT core hands back unexplored nodes and the SM must query again, which would also explain the input words OptiX leaves uninitialized on a first query. To be tested by resubmitting those words.
31. **2026-11-09, one SM saturates (coherent rays).** After moving the TTU group to fewer registers (only register fields changed, checked against NVIDIA's bytes), one SM can hold 32 warps. The steady completion rate levels off at about 0.134 rays per cycle (7.4 cycles per ray) from 20 to 32 warps.
32. **2026-11-09, Throughput_8 at saturation.** With 32 warps per SM, two sibling SMs (2k, 2k+1) each fall to 60 to 80% of their solo steady rate while two SMs further apart keep theirs. But a sibling pair delivers 1.25 to 1.4 times one saturated SM, not the same amount, so a single shared RT core with one SM's capacity per TPC is not confirmed; the one SM limit may be per SM, or the partial overlap of the two runs may inflate the pair total.
33. **2026-11-09, L1 is hard to evict on purpose.** In a plain CUDA control, strided loads from one warp (up to 4 MB) never evicted a warmed 16 KB working set from L1, and a second random chain evicted it only partly and not monotonically with size. L1 replacement is not simple LRU; the Memory_1 test needs a proven eviction method first.
34. **2026-11-09, rays can need several queries, and OptiX loops to resume them.** OptiX's traversal code resumes a ray by running the same TTU group again with the best hit distance as the new maximum and the returned pending nodes as input. Doing the same from our kernel gives the CPU's closest hit in every checked lane, for scenes up to 3 million triangles. Rays need 1.5 to 2 queries on average in moderately overlapping scenes and about 3.8 (up to 9) when triangles overlap heavily; scene size and ray direction matter little. Counting all queries, a finished ray costs about 2 to 10 times one query. (This corrects the earlier reading of "up to 4 node pointers".)
35. **2026-11-09, a query hands back at most two pending entries.** With a known number of triangles stacked on a ray, the first query already returns the closest hit and at most two pending entries, each an entry distance plus a node pointer; the follow up query then ends at once because both entries lie beyond the hit. Extra queries cost real work only when the first hit found is not the closest.
36. **2026-11-10, "2 pending entries" is not yet the stack depth.** A query returns at most 2 pending entries in every scene so far, but that is only the return format seen on a hit; the RT core may keep a deeper stack internally and return 2 only when it stops early. Traversal_2a to 2e test this.
37. **2026-11-10, BVH_5: traversal can start at any internal node, with no new instruction.** Putting an internal node of the GAS in the root word (store 0x180, same flags as the root) makes the RT core search only that subtree. In 37 runs (flat grids of 144 and 2,500 triangles and a four layer scene, starts one and two levels below the root, straight and oblique rays) every ray returned exactly the CPU's closest hit among the triangles inside the start node's box, and a miss otherwise, including 92 rays that cross the start node's box and would hit something outside it. Rays that need more than one query resume correctly from a subtree start. OptiX's instance level stays in front.
38. **2026-11-10, each skipped level saves one node fetch.** Starting one or two levels down saves 295 to 363 cycles per level when the BVH is in L2 and 610 to 650 when it comes from DRAM, the same as one dependent L2 or DRAM access in a pointer chase. A start two levels down in a 2,500 triangle scene costs about what a one level scene costs. For treelet or subtree queues this means the saving is real but per level, and a ray that misses inside its subtree learns nothing about the rest of the tree, so a correct closest hit still needs the rest searched. Memory_4 tests whether grouping rays by subtree adds a cache benefit on top.
39. **2026-11-10, GAS node boxes decoded; empty slot rule corrected.** Each child slot holds an 8 bit lower and upper bound per axis relative to the node's origin, scaled by a per axis power of two in the node header; the decoded boxes match the scene geometry. The earlier rule for empty slots was wrong for children at the top of a node's z range (it dropped real nodes in a layered scene); with the corrected rule every saved dump walks to the node count in its header. OptiX also places nodes in a different memory order each run, while the tree itself is the same, so nodes are named by their slot path from the root.
40. **2026-11-10, Memory_4: grouping rays by subtree cuts RT core memory traffic a lot and time less.** The same incoherent rays (random origins and directions) over a 6.2 MB and a 186 MB BVH, issued so that each warp's rays have their closest hit in the same subtree, versus randomly interleaved, all starting at the root. Grouped, the RT core fetches 24 to 46% fewer sectors from L2 per finished ray (43% with 65,536 rays), and cold runs read 24 to 46% fewer DRAM bytes per ray (45% with 65,536 rays). Throughput per finished ray rises 8 to 22% with 8,192 rays and 20 to 37% with 65,536 rays (denser groups). Every result matched OptiX; costs count every query of rays that need several. The node fetches go through L1 but are counted in neither the load/store nor the texture pipe.
41. **2026-11-10, Memory_4 (b): starting rays inside their subtree (oracle key).** Starting each grouped warp at the deepest node shared by its rays' subtrees (the treelet queue model) gives 1.14 to 1.68 times interleaved throughput and up to 57% fewer DRAM bytes per ray; starting each ray at its own subtree gives 2 to 5.3 times, in either order, because it skips every overlapping subtree elsewhere (queries per ray fall from about 2.0 to 1.5). **Both (b) results use an oracle grouping key: the subtree holding each ray's closest hit, known from a reference run.** A real scheme has to find the subtree without it (Memory_4a).
42. **2026-11-10, a ray's subtree cannot be read off the boxes.** In overlapping scenes the smallest child box containing a hit triangle is the wrong parent for 26 to 32% of hits. The hardware gives the right one: the leaf block of the hit, mapped to its node; leaf blocks can be shared by neighboring nodes' leaves. Keys built this way were confirmed by starting every ray at its key node (no wrong result in 81,920 rays).
43. **2026-11-10, in Memory_4 a third to a half of lane queries do no work.** When some lanes of a warp need another query, the whole warp runs again and finished lanes ride along. Whether those idle lanes cost RT core time is Throughput_2.
44. **2026-11-10, Throughput_2: idle lanes cost RT core time unless they are masked off.** With 16 warps on one SM, a warp with 1 active lane and 31 lanes that exit before the query runs 2.3 times as many warp queries per cycle as a full warp; the cost is roughly a fixed part per warp query plus about 7 cycles per active lane (cheap scene). Idle lanes that ride along with tmax 0 are not free: in a cheap scene each costs about three quarters of an active lane, and for rays that start inside the scene a tmax 0 lane costs about as much as a real query, because an interval of [0, 0] still passes every box that contains the origin. An empty interval (tmax below tmin) removes most of that but not all. Memory_4's resume rounds used tmax 0 for finished lanes, so its absolute costs per finished ray are inflated (equally for both orders); OptiX branches finished lanes out.
45. **2026-11-10, Memory_4a: without an oracle, grouping by the returned pending pointers buys almost nothing; packing does.** After the first query, almost every ray resumes at a different node (5,277 distinct nodes for 6,752 resuming rays in a 6.2 MB BVH, 7,497 for 7,682 in a 186 MB one), so sorting the resumed rays by pending pointer adds only 0 to 3% over simply packing the rays still running into full warps, which itself adds 8 to 15% over leaving finished lanes masked (OptiX's way). Without the oracle a ray needs about 30% more queries than with oracle per ray starts (1.88 vs 1.45, 2.00 vs 1.51). The oracle results of Memory_4 hold with finished lanes masked instead of riding along with tmax 0. A coarser grouping key (an ancestor of the pending node) is the next thing to try.
46. **2026-11-10, Memory_4b: on the whole GPU, grouping by subtree saves memory traffic but little time.** 262,144 random rays on the 186 MB BVH, all 142 SMs with 16 warps each: grouped rays get a 45% L1 hit rate instead of 17%, half the L2 fills, and about 400 to 500 fewer DRAM bytes per ray, but finish only 5 to 7% faster. The RT core's DRAM traffic here is about 140 GB/s, far below the GPU's bandwidth, so time is set by latency and by the last few resume rounds, not by bytes. Packing the rays still running into full warps between resume rounds is worth 17 to 26%. This is the first measurement whose working set exceeds L2 (RT core L2 hit rate 55 to 65%).
47. **2026-11-10, BVH_5b: short rays can start below the root without any oracle.** For each ray, descend from the root while only one child box touches the ray's segment; no other part of the tree can then hold a hit, so starting there is exact (every one of 8,192 rays in 48 runs matched both OptiX and a CPU reference). The gain is small with 4 warps (3 to 10%) and up to 1.7 times with 16 warps for the shortest rays, falling to a few percent as rays get longer, since fewer levels can be skipped when sibling boxes overlap. With root starts, short rays got less throughput at 16 warps than at 4, and local starts mostly removed that loss, which suggests contention on the shared top of the tree (not yet tested).
48. **2026-11-10, Traversal_2a: a query never returns without a hit.** In full traversal scenes (triangles parallel to the ray and just off it, so the ray visits every box and hits nothing), every query finished in one go, up to 262,144 triangles (depth 15, 34 million cycles in one query) and up to depth 38 with every sibling box overlapping. So there is no stack limit or work budget visible to the SM in these scenes; the RT core hands work back only when it finds a hit. A full miss costs about 130 cycles per triangle tested.
49. **2026-11-10, BVH_3: every custom primitive candidate costs one SM round trip of about 850 to 900 cycles.** With custom primitives whose intersection program always returns false (David's idea), OptiX calls the program exactly once per candidate per ray, and each candidate adds about 950 to 1,020 cycles to a trace, against about 110 to 130 for a triangle the RT core tests itself. So non triangle workloads pay roughly eight times more per candidate than triangle ones, before any intersection math. Also, a trace through OptiX that misses one triangle costs about 5,200 cycles from raygen, against about 1,600 for the same query issued directly, about 3,600 cycles of OptiX overhead per trace in this setup (Throughput_7 will measure it properly).
50. **2026-11-10, Throughput_8 with full overlap: the two SMs of a TPC share one traversal unit with about one SM's capacity (effective traversal capacity scales with TPCs: 71 on this GPU, 142 SMs, one TPC disabled).** With long coherent queries that keep the RT core busy for hundreds of microseconds (full traversal of 256 triangles, BVH in L1), two sibling SMs (2k, 2k+1) that overlap completely deliver 1.02 to 1.05 times one SM together, while two SMs in different TPCs deliver 2.0 times. The earlier 1.25 to 1.4 times came from blocks that overlapped only partly. This supports Cesar's claim of one RT core per TPC (another shared per TPC stage on the traversal path would look the same). For the model, C_inflight and the peak rate belong to the TPC, not the SM, and work on sibling SMs competes.
51. **2026-11-10, Memory_1: the RT core caches BVH nodes in the SM's L1.** Reserving shared memory at launch shrinks L1 from about 90 KB to about 20 KB (checked with a plain pointer chase). With the small L1, a trace repeated in the same kernel takes 1.9 to 2.5 times longer once its warp's rays touch more than one path's worth of nodes, and the same time when they do not. So shared memory use by the same kernel takes cache away from traversal, a cost the model and the DSL must charge.
52. **2026-11-10, Throughput_7 (partial): our measurement harness is not a throughput engine.** On the whole GPU OptiX traced the same 262,144 rays 11 to 22 times faster than our direct kernel, because the harness moves 768 bytes per lane and does one query per lane per launch with resume rounds driven by the host. From the one SM and per TPC measurements, the RT cores' peak on a cheap coherent query is about 24 rays per nanosecond, and OptiX reached about 8 (35%), so a lean direct kernel might gain up to about three times on cheap queries; measuring it needs a new looping kernel template.
53. **2026-11-10, Traversal_2b: the two returned entries are the next child plus a restart cursor.** In scenes where the first hit found is not the closest, the RT core visits a node's children in order of where the ray enters their boxes. On a hit it returns the nearest unvisited child explicitly and, as the second entry, the same node again with the index of the next child in that order and its entry distance, which stands for all remaining siblings. So two entries can cover any number of pending siblings at one level; how this works with unfinished work at several levels is still to be tested. Each extra query costs about a full query's fixed cost, and a query whose pending entries all lie beyond the best hit finds nothing; skipping it needs a distance check before resuming.
54. **2026-11-10, correction (Cesar): TTU register operands are ordinary registers on both architectures.** TTUST's second source and TTULD's second destination use ordinary registers on SM120 as well as SM89 (the SM120 field is only named Ra_URc), and all TTUST and TTULD register operands are even aligned 64 bit register pairs. An earlier version of this plan said SM120 used a uniform register. Our check of every TTU sequence now enforces even pair registers, and all sequences we ran satisfy it.
55. **2026-11-10, note on BVH_5: starting traversal at an internal node is already known to Cesar's group.** Our contribution there is the measurement: the latency saved per skipped level (one node fetch), exactness of local starts for short rays (BVH_5b), and the oracle bounds on subtree queues (Memory_4), not the trick itself.
56. **2026-11-10, Traversal_2b to 2e: how rays come back, and what it costs.** A returned entry can also be a whole internal node, and the restart cursor sits on the deepest unfinished node; leaf entries carry their own progress. How work at two levels at once is kept is still open. The number of queries a ray needs depends on whether the first hit found is the closest, not on how many hits lie on the ray, and the last query often finds nothing because the pending work lies beyond the best hit. Back face culling works through the ray flag words; terminate on first hit changes nothing inside the RT core (it returns on every hit anyway), so shadow rays are cheaper only because the SM stops resuming. Each return costs about one query's fixed cost (about 1,300 to 1,650 cycles across launches, about 740 in a warm kernel).
57. **2026-11-10, Memory_5: the shared traversal unit uses both SMs' L1 caches, about half each.** When one SM issues queries, its own L1 receives about 50% of the RT core's node fetches and the other half lands in one other L1; when both siblings of a TPC issue queries, each L1 receives its own half plus its sibling's half, and two SMs in different TPCs do not mix. So the two L1s of a TPC act as one node cache for traversal. For the model, the node cache capacity belongs to the TPC, and shared memory use by either SM of a TPC (Memory_1) takes cache away from both SMs' traversals.
58. **2026-11-10, Interface_5 (first test): two TTUGOs in one session do not fault or hang, but return no answer.** Submitting the same ray twice in one session (OptiX's stores and TTUGO repeated, then its six loads) ran without fault or hang in the same time as one query, but the loads returned neither a hit nor the usual miss record: mostly zeros and one word that looks like a status code. We stopped there, as planned. The session ticket register reads zero before a session and after it closes. Whether the .DUAL form of TTUOPEN expects another layout for a second query is open.
59. **2026-11-10, Memory_5 confirmed by timing: nodes fetched for one SM are at L1 speed for its sibling.** With the BVH warmed by a trace on one SM, the same trace on its TPC sibling in the same kernel takes 782, 827 and 867 cycles at one, two and three levels, exactly what a second trace on the warming SM takes (about 43 cycles per level); on an SM in another TPC it takes 1,682 to 2,385 cycles, the same as a cold L1 with the BVH in L2 (about 275 to 430 per level).
60. **2026-11-10, BITTU kill tests with NVBit 1.8.1: two pass, two fail.** NVBit can insert probes right before and right after a fused TTU group without breaking it (correct results, no hang) and can read the registers the group stores (all lanes correct). But its instruction list silently drops TTU instructions (the 19 instructions of the group are simply missing, visible only as a gap in the offsets), and its launch callbacks never see OptiX's own kernels. So BITTU on NVBit can work for kernels with TTU code that we or others compile directly, with its own decoder for the hidden bytes, while OptiX programs need the fallback of clock reads around optixTrace in raygen.
61. **2026-11-10, Throughput_4 (ALU part): independent ALU work after a traversal is hidden for free up to the traversal's own latency.** Placing up to about 1,000 cycles of dependent integer work after the query was issued and before its results were read left the query's latency unchanged (about 1,650 cycles for a cached one triangle scene, 2,330 for a 2,500 triangle one), with one warp and with eight; beyond that the warp takes the ALU time plus about 160 cycles. So an SM can overlap useful arithmetic with the RT core; the open part is whether memory traffic from the same SM slows the RT core.
62. **2026-11-10, Throughput_6: effective traversal capacity scales with TPCs (71 on this GPU: 142 SMs, one TPC disabled); random rays stop scaling at about 40 SMs.** With 32 warps on each SM and one block per SM, a coherent query (BVH in L1) gives 70.6 times one SM's throughput at 71 SMs (one per TPC), and only 73.5 times at 142 SMs, since the second SM of a TPC adds 4%. Random rays on a 6.2 MB BVH scale to 32 SMs (33.9 times), then plateau at about 42 times one SM (about 0.39 rays per cycle) from 64 SMs to 142; on a 186 MB BVH the plateau is 41.7 times at 64 SMs and falls to 33 times at 142. The plateau is not yet explained: the RT core's L2 traffic at that rate (about 46 sectors per ray, estimated 1.4 TB/s) is far from the L2 peak, and our harness's own register traffic is two thirds of the L2 requests, so a leaner kernel is needed to attribute it.
63. **2026-11-10, the random ray plateau is not caused by our harness.** A slimmed harness (same RT core instructions, byte identical; one 32 byte sector of input per lane, a shared record for the other inputs, 13 result words stored, no clock or register image stores) cut our own L2 requests from about two thirds to about 40% of the total, yet random rays still stop scaling at about 0.40 to 0.44 rays per SM cycle (about 38 times one SM on a 6.2 MB BVH) and get worse beyond 64 SMs on a 186 MB BVH. Even with one SM per TPC the scaling is already sub linear above 32 SMs, so sharing of the traversal unit is not the limit either. The RT core's own memory traffic per random ray is about 43 L2 sectors on the 6.2 MB BVH (all L2 hits, no DRAM) and about 68 sectors on the 186 MB BVH (L2 hit rate 100% at 32 SMs, 79% at 142, DRAM 470 bytes per ray at 142 SMs); on the small BVH the L2 is about half used and DRAM is idle, so neither bandwidth limit was shown at that point. The cause was found later: see the finding on the L2 sector rate and the per GPC limit below.
64. **2026-11-10, Throughput_7 (slim): OptiX is faster than our slim kernel, so there is no OptiX overhead to report.** On the same rays (71 and 142 SMs worth), OptiX finishes whole rays in 0.52 to 0.74 of the time our slim kernel needs for the first query only (random rays on 6.2 and 186 MB BVHs; 1.9 to 2 queries per ray), and in 0.2 of the time on a coherent one triangle ray. Per query OptiX is 2.6 to 3.6 times faster. So the earlier 11 to 22 times gap was our harness. Later ablations (Finding 78) showed that most of the remaining gap was our own load and store instructions, not an RT core limit: they cut it from 3.5 times to 1.6 times.
65. **2026-11-10, SM to GPC map.** The clock64 counter is one counter per GPC, so SMs can be grouped by reading it everywhere at once: 12 GPCs, GPC = (SM id / 2) mod 12, eleven with 6 TPCs and one with 5 (71 TPCs, 142 SMs). Consecutive blocks of a launch land on different GPCs.
66. **2026-11-10, random ray plateau: the L2 sector rate and a per GPC limit.** A plain pointer chase on a 6 MB table reaches 38 L2 sectors per SM cycle at 142 SMs (ncu: L2 at 99% of peak) and no more; load latency stays flat at about 280 cycles until the load nears that rate and then rises as Little's law says. One GPC moves at most about 6 sectors per SM cycle however many of its 12 SMs load, so 12 SMs packed in one GPC deliver half of 12 spread SMs. The slim random ray runs put 32 sectors per cycle on the L2, about 80% of the plain load ceiling (the RT core's own 45 sectors per ray plus our result stores), which explains the plateau; OptiX, without our stores, goes about twice as far.
67. **2026-11-10, Latency_3 and Latency_4: what a node, a leaf and a triangle cost.** A traversal that visits everything costs about 934 cycles plus 343 per node (one L2 round trip), 113 per leaf and 52 per triangle. Children of a node are handled in groups of three. An extra triangle in an existing leaf costs about 45 cycles against 156 for an extra leaf with one triangle; a leaf holds at least 4 triangles.
68. **2026-11-10, Memory_2: the node cache is the SM's L1.** Everything the RT core fetches is found again in a second pass while the footprint is below about 60 KB, half of it is lost at about 100 KB and all at about 700 KB; with shared memory reserved it cannot hold even a few KB. No larger separate cache shows up.
69. **2026-11-10, Memory_3: bytes per query.** A full traversal fetches about 176 bytes of header plus 128 per node visited and 43 per triangle tested; random rays in 100,000 and 3 million triangle scenes fetch 1.4 to 2.2 KB per ray.
70. **2026-11-10, Traversal_1: visit order and early exit.** Children and leaves are visited by distance along the ray, not by memory order; inside one leaf the triangles are tested in storage order and the first hit found is returned, so the first returned hit is not always the closest even in one leaf. Rays are cut at tmax: boxes beyond it are never visited (latency falls linearly with the part of the scene the ray reaches).
71. **2026-11-10, Traversal_4: the RT core matches exact arithmetic except on the edge itself.** Rays one float32 step or more off a triangle edge or vertex are classified exactly as in exact arithmetic; rays exactly on an edge follow an ownership rule (two edges count, the third does not, one vertex counts) and offsets of denormal size count as zero. OptiX gives the same answers because it uses the same unit. A shared edge between two triangles was not tested.
72. **2026-11-10, Model v1.** A simple per ray model (queries per ray, RT L1 sector requests, L2 fills and DRAM bytes as inputs; work that does not depend on the number of warps, latency hidden by warps, and a queueing term in warps) fitted on one SM data predicts held out ray orders and scenes on one SM to about 11 to 19 percent mean error. Fitted costs are consistent with the direct measurements: about 660 cycles per warp query matches the 740 cycle fixed cost, and about one L1 sector per cycle matches a plain load. With the TPC scaling and L2 sector ceiling terms it predicts whole GPU throughput of random rays to about 20 to 26 percent, with an overshoot of 15 to 50 percent beyond 71 SMs, and one coherent 64 triangle scene to 16 percent. It fails on the one triangle coherent case (about six times too slow): the queueing term was learned on random rays and there is no measured per node unit cost for coherent rays yet. The model takes measured per ray descriptors as input; it does not yet predict them from a scene.
73. **2026-11-10, Throughput_7 with the resume loop inside the kernel.** Our direct kernel now runs the whole ray (the same traversal group repeated in a loop in the kernel until the ray has no pending work, exactly as OptiX's own traversal loop rebuilds the next query) and every checked lane equals the CPU closest hit, with no hang. OptiX on the same rays is still faster: about 1.8 to 2.6 times on random rays at 71 to 142 SMs and 4 to 5 times on a coherent single triangle scene. So the earlier gap was not host round trips. Remaining differences from OptiX's own launch are one ray per thread, a launch of about 130,000 rays, and the input loads of our loop; the comparison says nothing yet about the RT core itself.
74. **2026-11-10, plateau check.** With the RT core's own traffic only (no plain loads), spreading active SMs over the 12 GPCs instead of packing them into as few GPCs as possible changes whole ray throughput by only 0 to 10 percent (packed slower below 36 SMs, equal at 60); the per GPC limit seen with plain loads (about 6 sectors per cycle) is not reached because the RT core asks for only about a sixth of that per SM. These launches are short (about 0.1 ms), so this is not a steady state test. Grouping random rays by the subtree they hit (an oracle key) lowers whole kernel L2 sectors per ray by 24 to 38 percent and RT L1 sector requests by 16 to 28 percent but raises whole GPU rate only 8 to 9 percent on a 6 MB scene (not at all on a 186 MB scene at all SMs, where DRAM utilization is about 60 percent in both orders), because at the plateau the L2 is at 70 percent (interleaved) or 47 percent (grouped) of its plain load ceiling and the rate of our kernel is set by costs that grouping does not change.
75. **2026-11-10, steady state (long launches) changes the OptiX comparison.** With a persistent kernel (each thread traces many rays, launches of millions of rays lasting 3 to 17 ms) every lane of every run equals OptiX and the CPU. On random rays our direct kernel stops scaling at about 36 SMs and reaches 825 rays per microsecond (small scene) and 726 (large scene), while OptiX reaches 3,000 and 1,760: OptiX is 3.6 and 2.4 times faster, and 10 times on one triangle. The earlier 1.8 to 2.6 was therefore not a launch effect. ncu shows OptiX with half our resident warps (13 against 27 per SM), more registers (113 against 72), about the same number of RT queries in flight (9 to 10 per SM), and 0.6 times our L2 traffic per ray. Our warps spend most of their time throttled in the memory instruction queue. Removing a third of our own harness traffic gives 32% more, which leaves a 2.8 times gap; why our queries complete more slowly at the same concurrency is not yet explained.
76. **2026-11-10, the plateau tests hold at steady state.** Packing active SMs into few GPCs costs 0 to 10% against spreading them (same as with short launches), and ray grouping by hit subtree gains 8 to 13% for our kernel but 2.0 to 2.2 times for OptiX on the same rays. One SM saturates at about 54 cycles per ray on one triangle from 4 warps, far above the one shot unit cost of 7.4 cycles, so the unit is not what limits our kernel.
77. **2026-11-11, what stands and what does not.** The one SM results (latency per level, cache behavior, TPC scaling on coherent rays, per element costs) stand. The whole GPU random ray throughput of our direct kernel, and the plateau seen in it, is limited by our own memory traffic (warps stalled in the memory instruction queue, 1.7 times the L2 sectors per ray that OptiX moves), so it is not a measure of the RT core; the earlier plateau explanations (Findings 62, 63, 66, 74, 76) describe our kernel, not the hardware. Key result: grouping rays by the subtree they hit gives OptiX 2.0 to 2.2 times, but our kernel only 8 to 13 percent, so the locality idea is strong on an efficient pipeline. The grouping key is an oracle, so the next test is a realistic sort (Morton code of ray origin and direction) on OptiX. Plan: future whole GPU throughput tests use OptiX with controlled ray order; our direct kernel is for single SM microbenchmarks.
78. **2026-11-11, most of the gap between our direct kernel and OptiX was our own load and store instructions.** In the persistent kernel on random rays (100,000 triangles, all 142 SMs), loading the lane invariant input words once instead of for every ray gave 66% more throughput, writing one coalesced 16 byte result per ray instead of 13 scattered words gave 17% more, and limiting the kernel to OptiX's 13 warps per SM gave none (but removed the memory instruction queue stalls, 14 stalled warps to about 1). All three together gave 2.3 times, which leaves OptiX 1.6 times faster instead of 3.5 times. Our kernel executes about 5 times fewer instructions per ray than OptiX, so instruction count is not the cause. The gain came with almost no change in L2 sectors per ray, so what mattered was the number of memory instructions through the SM, not the traffic. The remaining gap matches our 1.4 times more L2 sectors per ray. Every ray in every run still equals OptiX's answer. This confirms Finding 77: the whole GPU random ray rates of the direct kernel measure the kernel, not the RT core.
79. **2026-11-11, a Morton sort of the rays recovers the whole 2x that the oracle grouping gave OptiX; OptiX's own reorder (SER) recovers none of it.** On 8.4 million random rays per launch, sorting rays by a Morton code of their origin (4 to 5 bits per axis, a few rays per cell) gives OptiX 2.2 times on a 100,000 triangle scene and 2.5 times on a 3 million triangle scene, the same as or more than the oracle grouping by hit subtree (2.2 and 2.4 times). Adding a coarse direction code on top gives up to 2.5 and 2.6 times; sorting by direction first is poor. Coarse sorts recover less (2 bits per axis: 82% and 30% of the oracle gain on the small and large scene). The sort cost on the host is not included. Using OptiX's reorder call (optixReorder) with the same codes as hints, on random order, makes OptiX 7 to 18 percent slower instead of faster, so ray order has to be fixed before the launch.
80. **2026-11-11, how deep the subtree grouping has to go.** Grouping rays by the subtree they hit, with oracle keys: on the small scene grouping at the first tree level gives 1.3 times, the second level 2.0 times, the third 2.2 times; on the 3 million triangle scene (8.4 million rays) 1.2, 1.5 and 2.0 times, against 2.4 times for the full key. 81. **2026-11-11, the number of queries per ray can be predicted from the BVH on a CPU.** A CPU traversal over the decoded BVH (nearest child first, the RT core returns after every leaf that improves the hit, and the ray is resumed whenever anything is still pending) predicts queries per ray of 1.85 and 1.98 against 1.88 and 2.00 measured on the 100,000 and 3 million triangle scenes, and the same count for 94% of individual rays (within one query for more than 99.8%). 83. **2026-11-11, net Morton speedup with a GPU sort: it pays on large incoherent launches only, and only if the rays are not copied.** OptiX, closest hit, a GPU key generation (Morton code of the origin, 4 to 6 bits per axis, or a coarse direction code) and a CUB radix sort of 12 to 24 bit keys, timed together with the trace (10 launches, median; every sorted result equal to the unsorted one for every ray, no mismatches in any run). Launch sizes 1 million, 8.4 million and 33.5 million rays, scenes with 100,000 and 3 million triangles. Cost of the sort: key generation 0.05 / 0.4 / 1.6 ms and the sort itself 0.04 / 0.3 / 1.5 to 2.1 ms at the three sizes, together about half the trace time of the small scene at 8.4 million rays and less than the trace time of the large one. Copying the rays into sorted order and the results back costs much more than the sort (random 32 byte gathers and scatters: 1.6 and 1.8 ms at 8.4 million rays, 6.4 and 8.1 ms at 33.5 million). Random rays, speedup over the unsorted launch, trace alone / sort plus trace without copies / everything including both copies: 100,000 triangles 2.0, 2.4, 2.9 / 1.35, 1.4, 1.6 / 0.68, 0.52, 0.55; 3 million triangles 1.7, 2.4, 3.8 / 1.4, 1.7, 2.7 / 0.81, 0.76, 1.09. So sorting pays (above 1 even with the copies) only for 33.5 million rays on the large scene; without the copies (rays generated in the shader from their index, results written in place) it pays from about 1 million rays on, and the gain grows with the launch size and the scene size. Ray sets with structure: (a) camera rays from a pinhole in raster order are already coherent (a shuffled launch is 1.6 to 3 times slower), sorting them never pays (trace alone 0.9 to 1.05 times, net 0.5 to 0.6 of the raster launch without copies); (b) bounce rays (origin at the primary hit, random direction, in pixel order) gain 1.06 to 1.33 times from sorting the trace alone but lose once the sort is paid (0.7 to 0.8 without copies; they beat a shuffled order by 1.2 to 1.8 times); (c) short radius queries (random origin, random direction, length 0.05 or 0.2 of the scene width): length 0.2 gains like random rays (net without copies 1.25 to 1.4 on the small scene, 1.4 to 2.9 on the large one), length 0.05 costs so little to trace that the sort only pays on the large scene from 8.4 million queries (1.0, 1.6 and 2.5 times). Best key everywhere is the plain origin code (4 or 5 bits per axis); direction first codes are worse on random rays and only match it on camera rays. Rule of thumb: sort when the traced rays start in random places, the launch is millions of rays and the scene is bigger than the L1 and L2 can hold, and avoid physically moving the ray records.
84. **2026-11-11, Finding 82 checked against the CPU: unfinished work at several levels is what a stack does, but the exact entries returned are not reproduced.** The first query of the 32 random rays of Finding 82 was replayed on the CPU (nearest child first, depth first, return at the first leaf that improves the hit). The CPU stack holds pending nodes at two or more depths in 18 of the 32 rays at that point (the RT core returned two depths in 8, since it returns at most two entries). Of the 36 node pointers the RT core returned, 22 are among the CPU's pending nodes at that return; the returned set equals the top of the CPU stack in 15 rays (9 of them with nothing pending) and the nearest entries by entry distance in 11. So the claim that the RT core keeps unfinished siblings at several levels holds, while which two entries it hands back is not predicted by this simple model: the return point, the order in which entries are kept, or the decoding of the returned words differs. Run on saved data from the existing checked group, no new TTU run.

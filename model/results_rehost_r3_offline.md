## (1) OptiX's loop
- No TTUCCTL, fence, barrier or any other TTU instruction in OptiX's traversal function except the one group (also none in the whole 80 KB window besides the other groups): prediction 1 held.
- After the intersection program returns, OptiX does NOT go straight to the next session: it keeps the pointer it passed to the program, adds 8 bytes to it (the next record) and subtracts 1 from a count field of the word built from the answer's first result word shifted left by 17 (bits 22:17), and while that field is not zero it calls the intersection program again for the next record, without a new session. So one answer stands for a run of consecutive records: pointer to the first record, count in the low 6 bits of the answer's first result word's second half (R33 bits 5:0).
- Values written before a new session that differ from ours: this count driven loop is the one: OptiX runs the program count times per answer; our inline test ran it once. (The adjustments of the pending entry words that I saw in the same code are separate and not needed for the data here.)

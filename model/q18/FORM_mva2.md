# Queue 18: mean value analysis with traversal unit and hand off stations. Form frozen 2026-11-16 before any prediction was computed. CPU only.
Question: with a per TPC traversal unit station and a hand off station whose demands come from saturation throughputs (not fitted to the launches below), does the network predict the loaded callback latency and the launch time of (a) the growing radius kNN with the register heap (F138) and (b) Arkade with a device buffer (F144, F145)? Honest status of the test: the targets were already measured when this was written (F138, F144, F145); the guard is that every constant below is fixed from other data before the model runs on them, and nothing is refitted afterwards.

## Network (one TPC = two SMs, symmetric; one customer chain per SM with W customers = warps in flight, W from ncu, not an integer)
A customer is a warp; one cycle of a customer = one warp call of the callback program plus everything the warp does until its next call.
- ISSUE_a, ISSUE_b (queueing, one per SM, visited by its own chain only): demand f = floor cycles per warp call (F131: T_floor x SMs / calls). Multiplier 1 (the post hoc m = 2 of F143 is NOT used).
- TU (queueing, one per TPC, visited by both chains): demand D_tu = 32 e / X_tu cycles per warp call. e = lane efficiency of the launch (recorder, or the committed prediction where the recorder was not run), X_tu = 0.14 lanes per cycle per TPC, the saturated rate of short coherent queries with both SMs of a TPC (F105, 4070 Ti; F90 gives 0.097 for one SM). This is the fastest saturated rate we measured, so D_tu is the smallest per lane demand: it errs towards the unit being less busy. The random ray rate (0.010 to 0.013 per SM, F90) is not used: the traversals here are short and mostly L1 resident.
- HANDOFF (queueing, one per SM): demand D_h = 1 / rho_max, rho_max = the highest warp calls per cycle per SM seen in any of the non target launches of F133 (RTNN, RT-BarnesHut; kNN orig and Arkade are excluded because they are the stress cases). There is NO saturated measurement of the hand off path (BVH_3 is one warp latency, 875 cycles, F49), so this is a capacity upper bound derived from the busiest launch we saw, not a saturation test. The 875 cycle latency stays inside the delay.
- DELAY Z = max(C - f - D_tu - D_h_service, 0) per chain, where C = trace window cycles per warp call in the one warp per SM (small) launch of the same build (trace_warp_cycles / calls). Using the trace window instead of the whole raygen (F143 used the whole) removes the result write to pinned memory from Arkade's cycle; for the device buffer runs the small launch of the pinned build is used for C and L_unl (the callback does not touch the output buffer; assumption stated, untested) and the same per call values are used on both GPUs.
Solved with the Bard Schweitzer approximate MVA for two chains (continuous W): R_ck = D_ck (1 + sum over chains Q_c'k - Q_ck / N_c), X_c = N_c / (sum_k R_ck + Z), Q_ck = X_c R_ck, iterated to 1e-9. The issue only version (no TU, no hand off) is computed beside it with the same solver.

## Predictions (what is compared)
1. Loaded callback latency per warp call: L = R_issue + (L_unl - f) (queue residence at the issue station plus the unloaded rest of the callback; the TU and hand off residence lie outside the probe window of the callback program and reach L only through the throughput).
2. Launch time: T = calls / (SMs used x X) / 2.5 GHz, X = throughput per chain in warp calls per cycle (no constant c0, no miss term). 2.5 GHz for both GPUs, as in F131.
Targets: kNN register heap build, rounds 1 to 4 (4070 Ti, F138 logs; the original build is predicted too, as the contrast), Arkade device buffer, full program, on io (60 SMs) and on triton (142 SMs, floor and unloaded values per call taken from the io ncu and probe runs).
Error = log(predicted / measured). Measured: L from the loaded probe run, T from the probes off run (kNN) or the global timer span (Arkade).

## Written expectations (before any number)
- The TU and hand off stations are lightly used by Arkade (a warp call every 86,000 cycles per warp at 16 warps per SM is far below any unit rate), so the network cannot lift Arkade's L above the unloaded value much: Arkade L and T will be under predicted by 3 times or more (error -1 or worse). The reason is not in these stations: it is the latency of its dependent chain under load, which is a memory system effect none of the stations represents.
- kNN original is under predicted by 3 times or more for L (dependent chain through memory, F138).
- kNN register heap: L within a factor 1.5 (|error| under 0.4) in rounds 1 to 4 if the TU station carries some of the queueing, otherwise under predicted by about 2 times like the issue only network. T within a factor 2 in rounds 1 and 2, worse in rounds 3 and 4 where the any hit load grows.
- The TU station is the binding one for the register heap in rounds 3 and 4 (utilisation above 0.5); if its utilisation stays under 0.2 everywhere the added stations change nothing and the result is the issue only network again.
- What would count as a failure of the form: |error| above 0.5 for the register heap L in any round, or the network ranking the original and the register heap in the wrong order.

# Sched_2 redone: priority of a warp returning from the RT core, ALU warps inside the TTU block (2026-11-17, tethys RTX 4090 GPU 1; written BEFORE any run of the new builds)

Why redone (F211): the first design put the ALU load in a second kernel; it never ran beside the TTU kernel, so the "with compute" arms had no load. Now the ALU warps are in the same block (the F157 one launch pattern, one block on one SM): build_patch --aluwarps. Warp T of the block runs the checked Unit_1 TTU code (one warp, one query, scene par:16:s, ray hit, stage 1 = one TTUOPEN, TTUMACROFUSE 17, one TTULD.CLOSE; stage 0 = same code with NOPs). Every other warp (W-1 of them) is an ALU warp: after the block barrier it waits about 400 cycles (delay loop, few issue slots, so the TTU warp issues its group first), reads the clock, runs 600 iterations of 12 independent FFMA (8 accumulators) plus 3 loop instructions (9,000 issue slots), reads the clock, stores both clocks. No TTU instruction in the ALU path (check_seq B15 aluwarps rules, all builds ALL PASS, stage 0 and 1).
Facts used (not new): scheduler = warp id mod 4 (F210); two or three ready warps on one scheduler alternate equally; four or more stall free warps: the three highest ids run first and the rest starve until they finish (F210, one code shape, one SM); one warp alone issues one FFMA per cycle. The TTU warp's window (start clock after the barrier to end clock after the CLOSE wait) was 3,586 and 3,590 cycles for stage 1 and 80 for stage 0 (F211, alone arms; those two numbers are valid, the loaded arms were not).
Arms (W warps, TTU warp T; ALU warps per scheduler a): alone (W 1); lo4 (T 0, ALU on the other three schedulers only, a 0 on the TTU warp's scheduler); lo5 (a 1), lo9 (a 2), lo13 (a 3), lo29 (a 7), all T = 0 = the LOWEST id; hi5 (T 4), hi13 (T 12), hi29 (T 28) = the HIGHEST id of the block (a 1, 3, 7 ALU warps of lower id on its scheduler). Stage 1, 5 repetitions x 30 launches (first dropped) in rotating arm order, medians of the TTU warp's window; 1 block per launch.
Smoke gate (before any timed launch; the F211 mistake): stage 0 of every arm once, then ncu counters for W = 13 (stage 0 and 1): the ALU load exists only if (1) ncu sm__inst_executed_pipe_fma of the launch is within 5 percent of 12 x 600 x 12 = 86,400 FFMA warp instructions, (2) every ALU warp's window (JSON warp_clk, relative to the TTU warp's start) starts within 1,500 cycles of the TTU warp's start and lasts at least 8,000 cycles (alone) or the matching share, i.e. it overlaps the TTU warp's whole window. If not, no timed launch and the design is reported invalid.
Delta = median window of the arm minus the median of alone.
Predictions (from F210 and Sched_1 only):
 P1 (lowest id, other schedulers loaded) lo4: |Delta| at most 40 cycles (the ALU warps are on other schedulers); confidence 70 percent.
 P2 lo5: Delta 10 to 100 cycles (one ready ALU warp alternates with the TTU warp's few issue slots after the return); lo9: 20 to 200.
 P3 lo13 and lo29: the lowest id starves against three or more ready ALU warps on its scheduler: the return is served only after the ALU warps finish, so Delta of order the ALU run time: more than 5,000 cycles at lo13 (3 x 9,000 issue slots = 27,000) and more than 20,000 at lo29; confidence 65 percent. If instead Delta stays under 500 at lo13, a returning warp does NOT starve like a stall free one (return priority); confidence 25 percent.
 P4 (highest id) hi5, hi13, hi29: Delta at most 100 cycles in all three (the highest id issues first); confidence 65 percent.
Reading rules: P3 and P4 both held = "ordinary warp id priority applies to a returning warp, no special return priority"; P3 missed small and P4 held = "returning warps escape the starvation of F210"; P4 missed large = "the RT return itself is slowed by ready ALU warps whatever the id". Intermediate values are reported as numbers, no verdict. One SM, one TTU warp, one ALU code shape (FFMA); other loads, several returning warps and memory stalled ALU warps are not covered.
Limits (stated now): the ALU load starts 400 cycles after the TTU warp's start, by design, so the arms measure the return, not the issue; the delay is a loop, so ALU warps are never exactly synchronous; 30 launches x 5 repetitions give run to run medians only; no ncu on the timed runs.

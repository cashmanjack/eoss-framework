# Model check: per call OptiX overhead and tmax in the replay (2026-11-16, no GPU run, no refit)

Question: does the performance model include OptiX's per call SM overhead (about 4,000 cycles at one warp, F178) and tmax in the replay? If not, what changes on the existing validations if it is added?

## 1. Per call overhead: NOT in the model
- Model terms (model/performance_model.py): harness fitted terms of a query (fixed 740 warm, per node, leaf, triangle), L1/L2/DRAM, contention, payload occupancy, TPC unit, L2 capacity. The raygen and optixTrace call code of OptiX (1,143 warp instructions, F178) is in none of them. Where it shows up indirectly: the RTNN refit constant c0 (50 to 420 cycles per query per SM, F127) and the callback floor F131 (callback functions only, not the raygen).
- Size at saturation (assumption, not measured): the 4,000 is latency at one warp; with W warps in flight it falls to about 4,000 / (32 x W), and the issue limit is 1,143 instructions / (4 per cycle) / 32 lanes = 9 cycles per ray per SM. F169's saturated point query launch (28 to 42 cycles per query per SM in total, triton) bounds it from above. So o = 9 to 28 cycles per ray per SM, added to both orders equally (additive, same for every ray order).
## 2. What changes on the validations if o is added (additive, nothing refitted)
- F113 (4070 Ti bounce rays, speedups of six orders over pixel order, rms log error 0.087 / 0.103 as published, reproduced here): pixel order cost 52.8 (100,000) and 68.4 (3 million) cycles per ray per SM (3.45 and 4.87 ms, 60 SMs, 2.6 GHz assumed, not checked under load). o = 9: 0.101 / 0.123; o = 28: 0.129 / 0.157. WORSE: the Morton prediction improves (1.18 to 1.15 or 1.11 against 1.10 measured) but the deep oracle orders, already predicted too low (1.12 against 1.26), fall further. Mean signed error -0.013 to -0.024 to -0.039 (100,000).
- F100, F117 (random rays, predicted speedups too small by 0.28 in log): an additive o shrinks every predicted speedup toward 1, so these get worse by about 0.02 to 0.06 (estimate: at 100 cycles per ray, 1.40 becomes 1.37 or 1.33; not recomputed per point). The cause named there (miss slope fitted on the harness kernel) is a different and larger term.
- F127 (RTNN absolute times, 132 to 1,272 cycles per query per SM): predictions rise by 9 to 28 cycles, 0.7 to 2 percent at the largest radii and 7 to 21 percent at the smallest. With the refit (c0 is fitted on the same data) c0 absorbs it and nothing changes except that c0 becomes o smaller; without a refit it adds to a model that is already wrong by 0.3 to 0.6 in log, so it is a small term there.
- F169 (1 candidate point queries, model 2.8 times too high): worse, 3.0 to 3.6 times, unless c0 is reduced by the same amount. The c0 of F127 already contains the overhead, so adding it to c0 would count it twice.
- F178 itself: the one warp gap is the overhead (4,528 to 4,663 cycles between OptiX and harness loop, same in 8 scenes), so a one warp OptiX prediction needs the term; whole GPU predictions get it only as o above, which lies between 9 and 28 and is NOT measured at saturation. A measurement exists in principle (OptiX launch with an empty raygen call against a launch without optixTrace, many warps); not run.
## 3. tmax in the replay: YES
- model/replay (replay.cpp, replay_aabb.cpp, reuse*.cpp) read Ray8 with tmax: the slab test uses [tmin, best] with best starting at tmax and shrinking with hits, so rays with short tmax visit fewer nodes in the replay. Validations: bounce and random rays use tmax 1e16 or a scene sized one (no effect); RTNN, kNN, Mochi use tmax 1e-16 or a radius, and the replay counts match the recorder (F125 to F127, F166, F167).
- Not checked: the replay against F182 (nodes and requests against tmax 0 to unlimited on the soup; at tmax 0 the replay should count the nodes that contain the ray origin, which is plausible against the measured 21 requests per ray and 37 percent of the time, but I did not run it: the replay binaries are not on tethys). Not in the TIME model: tmax acts only through counted nodes and queries, so the 37 percent time floor of a zero length ray (F44, F182) comes from the fixed cost term, not from the replay.

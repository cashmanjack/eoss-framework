# Sched_2 redone: a warp returning from the RT core against ready ALU warps in the same block (2026-11-17, tethys RTX 4090 GPU 1; predictions model/predictions_sched2.md, commits a9b2e7e and the addendum 8e02eac, before any stage 1 launch of the new builds). Raw JSON, CSV and logs notes/sched2 (private); analysis model/analyze_sched2b.py.

Design (see the predictions file): one block of W warps on one SM, warp T runs the checked Unit_1 TTU code (one query, 3,569 cycles alone), the other W-1 warps are ALU warps (47 iterations of 192 independent FFMA, start about 480 cycles after the TTU warp's start, run 10.9k cycles alone per scheduler, 28.7k with 3 ALU warps per scheduler, 61k to 65k with 7). New harness code: build_patch --aluwarps, check_seq rules (all builds ALL PASS, stage 0 and 1). Runs: stage 0 smoke (8 arms, 3 builds of the ALU body), ncu counters W = 13 stage 0 and 1, one stage 1 launch W = 4, then 9 arms x 5 repetitions x 30 launches (45 runs, 36 seconds), no fault, GPU idle after.
Smoke gates (load exists, the F211 mistake): ncu sm__inst_executed_pipe_fma 108,340 for W = 13 in both stages (expected 12 x 47 x 192 = 108,288), all on one SM; every ALU window starts 469 to 680 cycles after the TTU warp's start and ends after the TTU window in every timed run (minimum ALU end 10,903 against a TTU window of 3,500 to 4,800). Three designs of the ALU body were needed (12 FFMA per iteration was 33 percent ready, 192 FFMA had register bank conflicts, final 1.19 cycles per instruction alone), all in stage 0 before any TTU launch; the first two were not used for any result.

Reading (by the rules written before): P3 missed and P4 missed large, so "the TTU warp's return is slowed by ready ALU warps on its own scheduler whatever the id", not the starvation of F210 and not a return priority. Numbers: no effect from ALU warps on the other three schedulers (+8); with ready ALU warps on the same scheduler the window grows about 110 to 150 cycles per ALU warp for the lowest id (108, 122, 149 for 2, 3, 7) and about 46 to 60 cycles per ALU warp for the highest id (60 and 46 for 3 and 7); at 7 ALU warps per scheduler the window is 9 percent longer for the highest id and 29 percent for the lowest. So warp id still matters (the highest id loses 2 to 3 times less) but a returning warp is not starved by stall free ALU warps although F210 starved the lowest ids of stall free streams; the TTU warp's own instructions after the return are a short dependent sequence, which F210 found is not starved. Not found: the mechanism, how many instructions the TTU warp issues after the return (not counted), what happens with several returning warps (many TTU warps) and with memory stalled ALU warps.
Limits: one SM, one TTU warp, one ALU shape (FFMA), ALU warps start 480 cycles after the TTU warp by design (the arms test the return, not the issue); medians of 30 launch runs, runs of the 29 warp arms vary by 10 percent; no loaded multi warp TTU case, so this cannot explain the loaded callback latency (F133) by itself: at most 50 to 150 cycles per ALU warp on a 3,500 cycle window.

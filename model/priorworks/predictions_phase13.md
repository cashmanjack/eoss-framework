# Predictions, Phase 13 (2026-11-18, triton GPU 1). Written before any calibrated run and before any BITTU run.

Disclosure of what I looked at first (design smoke, one cell, not a result): one RTNN run on uniform 1M K 50 with 20,000 random queries (2 percent) as -q file. It showed (a) RTNN with a query file takes a different code path (points are sorted separately, "sort points" 15.5 ms) and (b) a 2 percent launch is far from saturating the GPU: search compute 1.04 ms (real build) and 0.96 ms (stub build) against 9.14 ms for the full run, so 50 times the subset time (52 ms) would be 5.7 times too high. I know this before writing the predictions below; they are written with it in mind.

## A. Calibrated prediction for the blind pipeline (model v1 form unchanged)
Change to model/priorworks/blind_pipeline.py: after the CPU replay and before commit 1, the script runs RTNN on a random subset of the queries (primary 2 percent, diagnostic 10 percent; seeded, sorted by file position, taken from the first N rows; the points are all N), 3 reps each, and measures the callback cost two ways. The full N queries are then predicted with the form of FORM_combined_v1.md unchanged: T = max(T_thr, T_chain), T_thr = (110 + (4.9 + cb - cbref) q_mean) N / (SM x CLK), T_chain = q_max x 575 / CLK; cbref = 1.011 cycles per candidate (the uniform reference of score_model_v1.py, recomputed from its data files; the K 50 value is used for every K, as in F250).
- Variant S (the callback cost as v1 defines it, F216 b): cb = (T_real - T_stub) x SM x CLK / (Nq x 1.10 x C_mean_subset), RTNN real build against the stub build (free intersection program) on the same subset, search compute median of 3. cb is floored at 0 (the stub also drops the stop after K hits, so real can be faster than stub); (4.9 + cb - cbref) is floored at 0.
- Variant D (direct): the per candidate cost solved from the real subset launch under the same form: (4.9 + cb - cbref)_D = (T_real_sub x SM x CLK / Nq - 110) / q_mean_subset - 4.9, floored the same way. Same form, the callback cost is the one that reproduces the measured subset launch.
- Fixed costs (not part of the form): geometry upload + query sort + point sort of the real subset run, median of 3, used as the predicted fixed part of RTNN's total (the full run reports query sort + geometry; the subset run reports the point sort separately).
- Winner call (pre registered, the pipeline's rule): RTNN if (predicted launch + calibrated fixed) < measured hubs time, else hubs. Call A (launch only, the pipeline's old rule) is reported next to it. Variant S feeds the call (v1's own definition); D is reported as a diagnostic, and if S fails and D does not, the pipeline default is changed to D after the results and that is stated as post hoc.
- Test: the 8 F245 datasets at K 5, 50, 128 (24 cells), each through the pipeline (replay radii by the pipeline's own 99 percent recipe, hubs and RTNN timed again after the committed predictions; F245 numbers are known, so this is NOT blind, but the order is proven by the commits). Quantity: measured RTNN search compute (median of 3) over predicted launch, inside 0.5 to 2 is a hit. Winner: RTNN (query sort + geometry + search) against hubs, per cell, against the "always hubs" count of the same run.
Predictions:
1. Variant S: at most 6 of 24 cells inside a factor 2 (it is v1 with a callback cost that F216 found to be 7 to 11 percent of the time, and the 2 percent stub difference is a few microseconds). Probability 75 percent. The floor on cb binds (real not slower than stub) in at least 8 of 24 cells: 60 percent.
2. Variant D at 2 percent: at least 12 of 24 inside a factor 2. Probability 30 percent. It over predicts on the unclustered sets (underfilled subset launch, the smoke gave 5.7 times) and may under predict on the clustered ones (a random 2 percent of queries has a sparser neighbourhood than the full set). At 10 percent: at least 12 of 24: 55 percent.
3. The calibrated winner call (S) is right in no more cells than always hubs (16 of 24 in F250; the count of this run is what is used): probability 70 percent. D beats always hubs strictly: 25 percent.
4. The calibrated fixed part is within a factor 1.5 of the measured query sort + geometry in at least 20 of 24 cells: 70 percent.
5. No cell fails to run (rc 0 everywhere): 80 percent. (The stub builds at K 5 and 128 were built in Phase 12 and are used here for the first time on a query file.)

## B. BITTU compute mode on the RTX 6000 Ada (GPU 1), validated sequences only
Plan: rebuild the NVBit tool (bittu/compute/build.sh) and the checked setup3 builds (stage 0 twin and stage 1, single level group, one warp) in /dev/shm on triton from the project's own scripts; check_seq ALL PASS before any run; then, under timeout -k 2 30, smallest launch first (one warp, 1 launch, then 5), the stage 0 twin under the tool first, then the stage 1 group under the tool, then the plain harness run for comparison; stop on the first fault, hang or refused check. Measures: decoded group shape, instance count, ray and result registers against the plain run, probe cost, corrected group time against the harness clock (the F122 method). No other TTU sequence is run.
1. The tool decodes the same group (fuse count 17, six predicated stores, six loads, close bit on the last load only) and refuses nothing it should accept. Probability 90 percent.
2. Counts exact: one group instance per active lane in every launch, full warp masks; the ray registers (8 words) and result registers (22 words) equal the plain run in all 32 lanes. Probability 85 percent.
3. No fault, hang or timeout in the stage 1 run under the tool. Probability 85 percent.
4. Probe cost (two clocks at the same point) between 1,300 and 1,600 cycles. Probability 60 percent (4070 Ti: 1,450).
5. Corrected group time within 3 percent of the harness clock at depth 1 (4070 Ti F122: 0.7 percent): 65 percent. Within 10 percent: 85 percent.
6. The raw probe to probe window is again several times longer than the harness clock (more than 4 times): 85 percent.
7. The build or the tool's NVBit load fails the first time for a reason unrelated to the hardware (driver, paths, missing /dev/shm files): 50 percent.

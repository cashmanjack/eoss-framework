# RTX 5090 (pc14), session 10 predictions, 2026-11-19. Written BEFORE any run of the programs below (OptiX and plain CUDA only, no TTU code of ours).

Questions. (A) Does OptiX 8.1 have any option that makes the built in sphere report a hit when the ray origin is inside the sphere? (B) Kill test: a fixed radius neighbour search with built in spheres that needs entry only hits (ray from q minus 2r along d, length 2r, any hit program keeps points at distance at most r). Is it exact, and is it faster than RTNN style custom AABB spheres or CLOVER hubs?

Disclosure: I have read F428 (the built in sphere reports the entry root only, no exit hit for rays that start inside; on the 5090 it runs in the RT core and is 2.4 to 3.0 times faster than a custom primitive on random rays with a closest hit program), F245 (triton table: uniform 1M K 5: hubs 89.6, RTNN knn 37.5 ms; K 50: hubs 105.8, RTNN 46.3 ms; RTNN loses to hubs on the clustered real sets) and the OptiX 8.1 programming guide section 9.6 (it says a ray may start inside a sphere and the reported single hit is a back face hit; F428 saw no such hit). I have not run anything for B.

## A. Inside origins (one small OptiX program, built in sphere, one sphere, rays from inside)
Variants: origin at the centre, at 0.5 r, 0.99 r, 1.01 r (outside, control); closest hit, any hit (geometry flag without DISABLE_ANYHIT), geometry flag DISABLE_TRIANGLE_FACE_CULLING, ray flags CULL_BACK_FACING_TRIANGLES / CULL_FRONT_FACING_TRIANGLES / CULL_DISABLED_ANYHIT, tmin 0 and a small tmin, direction along axes and diagonal. Header search: no sphere specific flag exists in optix_types.h 8.1 (the sphere array has only the geometry flags and SBT fields; the face culling flags name triangles).
1. No option in the 8.1 headers or guide is specific to spheres starting inside: 90 percent.
2. The built in sphere reports NO hit (closest or any hit) for origins at the centre, 0.5 r and 0.99 r in every flag variant I try, consistent with F428: 70 percent. The guide statement (a back face hit with optixIsBackFaceHit) holds on the 5090 in at least one variant: 25 percent. Mixed (hit for some origins, e.g. very near the surface): 5 percent.
3. The control (1.01 r, entry in front) reports the entry hit with t within 1e-5 relative of the exact value in every variant: 95 percent.

## B. Fixed radius search
Data: uniform 1M (the F245 file recipe: numpy default_rng(11) random((1e6, 3)) float32, unit cube) and a clustered synthetic set: 1M points, 50 Gaussian clusters of 20,000 points, centres uniform in [0.1, 0.9]^3 (seed 7), isotropic sigma 0.02 (seed 8). Every point is a query (hubs' convention: the query point counts as one of the K neighbours, F245). K = 5 and 50. Radius r = smallest radius at which 99 percent of 3,000 sampled queries have K points inside (self included), from a kd tree (the F245 recipe), so about 1 percent of lists are short by construction. The lists are the K nearest points inside the ball (nearest first), by insertion into a per thread list in all RT arms (same insertion code).
Arms (all on the 5090, one GAS build plus one launch, device scope, data on the device, no result copy, median of 5 after one warm up):
- SPH: built in spheres of radius r(1 + 5e-4), ray origin q minus L d, direction d fixed (1, 0, 0) (a fixed direction, not tied to the data), tmin 0, tmax L = 2 r (1 + 1e-3); any hit program computes the exact float distance of the point to q, inserts if at most r, always calls optixIgnoreIntersection. Why exact: a point p with |q - p| at most r has |o - p| at least L - r > r(1 + 5e-4), so the origin is outside its sphere, the line enters it before q, so the entry root lies in (0, L].
- CUS: custom AABB primitives (cube of side 2r around each point, what RTNN builds), ray from q with tmax 1e-3 r, intersection program computes the distance and inserts, reports nothing (RTNN style).
- HUBS: CLOVER hubs (bitonic-hubs, F227 harness clover_bench.cu, its own span, includes its index build; exact kNN, no radius).
- Real RTNN (knn mode) only if its build for K = 5 and 50 on sm_120 takes under an hour; otherwise not run and reported as such.
Candidates per query: SPH = any hit calls, CUS = intersection program calls (a counter per query, a separate launch from the timed one so counting does not change the timing); HUBS: not instrumented (CLOVER's distance computations are not counted by its code).
Reference: the exact ball counts (points within r, self included) and the K nearest from a kd tree on 20,000 sampled queries (float32 coordinates as doubles, tolerance 1e-6 relative on the distance, ties are not errors).

Reading rules written now:
- Radius per cell is fixed from the kd tree before any GPU run and printed; the same radius goes to every arm. HUBS has no radius.
- A cell where CUS or SPH output does not match the kd tree on any sampled query is reported as "not exact" with the counts; its time is still given but marked.
- "Faster" uses the median of 5 timed repetitions; spread (min to max) is reported. One data set draw, one GPU.
- Launches: queries are launched in chunks sized so that no launch exceeds 3 s (display watchdog); the time of a cell is the sum of its chunk launches plus the GAS build, measured with events around the whole span. The first run of every arm is a 10,000 query smoke test.
- Run rules: pc14_gpucheck.sh before every process, timeout -k 2 30 (60 for the 1M cells if a smoke run shows they need it), GPU 0, smallest launch first, stop at the first fault, hang, timeout, or wrong result, raw files timestamped and opened with mode x.

# Queue 19: mean value analysis with L1, L2 and DRAM stations (last try). Form and kill rule frozen 2026-11-16 before any prediction was computed. CPU only.
Question: if the issue station of F149 is split into separate issue, L1, L2 and DRAM stations, with per call load counts and the RT unit's node fetches added, does the network predict the launch time of the 8 growing radius kNN launches (original and register heap build, rounds 1 to 4, 4070 Ti, F138 logs) to rms log error 0.3 or less?
Honest status: the targets were measured before this was written (F138, F149 already compared an issue only and a TU plus hand off network on them: rms of the launch time error 0.44 to 0.82). The guard is the same as in F149: every constant below is fixed from other data before the model runs, and nothing is changed after seeing a result.

## KILL RULE (fixed now)
Error = log(predicted / measured) of the launch time T. If the rms of that error over the 8 kNN launches is above 0.3, MVA is dropped as a model of the callback side: it is not used for the paper's model, F143 / F149 are reported as a negative result, and no further variant is tried in this project. If it is 0.3 or below it is kept only as a description of these kNN launches (one program, one chip), not as a general result. The rms of the loaded callback latency L is reported beside it but is not part of the rule. Arkade is not part of the rule (no replay and no per launch hit rates for it here) and is not predicted in this test.

## Per call demands (SM cycles per warp call of the callback program; a call = what the probe counts as f0_calls)
Counts of the callback functions (SASS functions called more than 1.5 times per warp) from the ncu source counters of queue 13 (notes/q15/ncu, model/callback_counts.py): warp instructions, L1 tag requests (global), local loads and stores, L2 theoretical sectors per call, and the kernel level L1 hit rate of global loads h of the same launch. BITTU is not used for them: it does not instrument OptiX's programs (F118, the recorder mode only counts intersection calls), so the per call load counts are the ncu counts of the same programs. Costs are the F131 constants (model/results_callback_cost.md): c_i 0.25, c_tag 1.00, c_x 1.90 per sector that misses L1 and hits L2.
- ISSUE (own SM): D_i = sum over callback functions of calls x (warp instructions x 0.25) / probe calls.
- L1 (own SM): D_l1 = [sum over callback functions of calls x (tags + local loads + local stores) x 1.00 / probe calls] + n_f x 1.00, where n_f = RT unit node fetches per warp call = (nodes per query from the CPU replay of the round, model/predictions_knn_4070ti.md first table, rand order) x active queries / 1.1 / probe calls. The 1.1 is the lane sharing ratio of random rays in natural order (F123); one tag per node fetch.
- L2 (own SM): D_l2 = [sum over callback functions of calls x (1 - h) x L2 sectors x 1.90 / probe calls] + n_f x 4 sectors x (replay share of fetches beyond 480 lines, same table) x 1.90.
- DRAM (own SM, fair share): D_d = lts sectors of the launch x (1 - L2 sector hit rate) / probe calls x 9.52 cycles. 9.52 = 60 SMs / (504 GB/s / 32 B / 2.5 GHz) = the 4070 Ti's specified DRAM bandwidth divided evenly over the SMs, the optimistic end (the measured random line cost of 32 cycles per sector in F131 is a TLB and page miss cost and would put DRAM above the launch time, so it is not used). The two launch totals come from the ncu run of the same launch (measured inputs, like h).
- TU (per TPC, shared by both SMs) and HANDOFF (own SM): as in F149 (model/q18/FORM_mva2.md): D_tu = 32 e / 0.14, D_h = 1 / rho_max.
- DELAY Z = max(C - D_i - D_l1 - D_l2 - D_d - D_tu - D_h, 0), C = trace window cycles per call in the one warp per SM launch.
Solver: the Bard Schweitzer MVA of F149 (model/q18/mva2.py solve), two chains, continuous W warps in flight (ncu).
Predictions: T = calls / (60 X) / 2.5 GHz (no fixed term, no miss term beyond the above); L = sum of the residence at issue, L1, L2 and DRAM + max(L_unl - their demands, 0).
The F149 issue only prediction (one station with demand f = max(issue, memory) of F131) is recomputed beside it with the same inputs, to show what the split changes.

## Written expectations (before any number)
- The node fetches are small next to the callback's own loads (the register heap build's any hit does about 600 tags per call in round 4, the node fetches 5 to 10 per call), so n_f changes D_l1 and D_l2 by 1 to 3 percent.
- Splitting f into tandem stations (sum instead of max) raises the total demand a little and lowers the queueing at each station, so I expect T within 10 percent of the F149 issue only values: kNN still under predicted in all 8 launches, rms about 0.4 to 0.6.
- DRAM demand is small (a few percent of D_l1 + D_l2) except maybe in rounds 1 and 2 of the original build.
- Therefore I expect the kill rule to fire. A pass would mean the memory side demand was missing from F149's floor, which I do not expect.

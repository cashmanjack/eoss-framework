# RTX 5090 (pc14), session 9 predictions, 2026-11-19. Written BEFORE any run of the Sphere_1 programs on this GPU (OptiX only, no TTU code of ours).

Question: the RTX Blackwell whitepaper says the 4th generation RT core intersects spheres and linear swept spheres in hardware and has twice Ada's ray triangle rate. (A) Does the OptiX built in sphere run in the RT core on the 5090 (no SM instructions per candidate), and what does that do to the cost per candidate against a custom primitive and against tessellated triangles (F204 repeated)? (B) How does the 5090's cost per triangle compare with Ada's (F67 latency terms, F194 rate) at one warp and at saturation, against the whitepaper's 2x?

Disclosure: I have read F204 (4090 results) and my own 5090 TTU results (F405 to F412: second trace 790 against Ada 782, warm and cold launches 9 to 32 percent above Ada because L2 349 and DRAM 862 cycles; Throughput_1 gap rate 0.158 to 0.162 against Ada 0.14 to 0.148; Throughput_6 long coherent queries 0.0277 rays per cycle per SM against 0.0178 on Ada, a factor 1.56). The SDK is OptiX 8.1 headers (sphere build input and built in sphere module exist; the linear swept sphere API is not in 8.1, so only spheres can be tested). The driver (580.126.09) decides what the built in sphere program is; I do not know whether it uses the hardware path through an 8.1 ABI call.

Programs: ttu/bench/Sphere_1 (F204's: sphere.cu, sphere_dev.cu, run.py, model/analyze_spheres.py) built with nvcc sm_120, PTX compute_120, plus one new scene kind `stack` (N one triangle candidates, same xy, stacked along z, axis ray inside every box and outside every triangle, identical lanes), added only for part B. NSM = 170. Same designs as F204: D1 (axis 1.27 r from every centre, N = 1, 4, 16, 64, 256), D1b (1.018 r, near miss), D2 (20,000 random spheres, random rays, r 0.02, 0.04, 0.08), ncu (smsp__inst_executed.sum at N = 16, 64, 256, saturation launch of 1,048,576 rays), one warp = identical lanes, 12 launches, median. Stack scene: N = 1, 4, 16, 64, 256, 1024, 4096 one warp and saturation (4,194,304 rays).

Ada values used (F204, 4090): one warp slope per candidate S 1,341, C 1,226 cycles; saturation S 3.45, C 3.00 cycles per ray per SM (96 SM cycles per warp call); ncu warp instructions per candidate S 215 to 245, C 190 to 230, T arms 0; D1b saturation T0 4.46, T1 7.24; D2 saturation S / C 0.84 to 0.97, T0 / C 0.98 to 1.07. Triangle terms: F67 52 cycles per triangle, 343 per node, 113 per leaf (one warp latency, L2 warm L1 cold); F194 saturation 0.67 cycles per triangle per SM, 1.3 per node, leaf slot 0.06 (identical lanes).

Predictions (probability that the statement holds in brackets):

A. Spheres
1. Built in sphere is NOT in the RT core on the 5090 under this OptiX 8.1 call path: S ncu warp instructions per candidate above 50 (S is SM resident by the F204 rule): 45 percent. The hardware reading (under 15 per candidate, flat over N, as the tessellated arms): 45 percent. Between 15 and 50 (partial): 10 percent. I cannot argue strongly either way: the whitepaper says hardware, but the sphere type was introduced in OptiX 8.0 for Ada and the driver may pick the new path only when it is told to (for example by an OptiX 9 ABI); the F204 SM count on Ada was the hardware at the time.
2. C (custom primitive): ncu warp instructions per candidate 150 to 280 (Ada 190 to 230; different SASS per architecture): 75 percent. One warp slope 1,150 to 1,600 cycles per candidate (L2 349 against 290 adds a few percent; the SM part equals Ada): 65 percent. Saturation slope 2.3 to 3.5 cycles per ray per SM: 65 percent (the SM issue limit is the same, 2,595 MHz against 2,520 does not change cycles).
3. If S is SM resident (statement 1 first branch): S and C within 20 percent of each other at one warp and at saturation, and in D2 S / C between 0.85 and 1.05: 75 percent given SM resident.
4. If S is in the RT core (second branch): one warp slope per candidate under 600 cycles (central 350: near a F67 leaf plus triangle, no SBT dispatch): 65 percent given hardware; saturation slope under 1.5 cycles per ray per SM (central 0.8): 60 percent given hardware; D2 S / C between 0.3 and 0.8: 55 percent given hardware; S has no instruction growth with N.
5. S and C find the same hit (hit flag and sphere index agree on at least 99.9 percent of D2 rays): 85 percent, t within 1e-4 relative for 99.5 percent: 70 percent (the hardware test could round differently from my program; this is the item most likely to fail if S is hardware).
6. Tessellated arms (T0, T1): D1b saturation slopes within 30 percent of the Ada values (4.46, 7.24) in cycles per sphere: 45 percent; (the 5090's triangle rate is higher, see B: I expect them lower, 2 to 5): 45 percent; D2 T0 / C between 0.6 and 1.15 at every radius: 60 percent. Hit fraction of T0 and T1 unchanged from F204 (geometry only): 90 percent.
7. D2 saturation cycles per ray per SM, C: r 0.02 / 0.04 / 0.08 each within a factor 1.4 of the 4090 value (86 / 103 / 263): 55 percent (SM bound parts equal, memory differs).
8. GAS sizes: S about 1 MB, C 0.7 MB, T0 about 25 MB, T1 about 100 MB for D2 (same builder, driver differs): 70 percent each within 30 percent of the 4090.

B. Triangle rate (stack scene, OptiX only; compared with F194 and F67 from the Ada TTU runs; no Ada OptiX stack run exists, so the comparison uses my 5090 TTU data and the Ada published terms, mixed method, labelled)
9. One warp, slope per extra triangle over N = 1 to 4096 (identical lanes, L2 warm, L1 cold): 40 to 70 cycles per triangle (F67 52; the second trace on the 5090 equalled Ada, so the unit latency is the same): 55 percent. Ratio to 52 between 0.8 and 1.3: 70 percent. NOT below 0.6 (no 2x in latency): 85 percent.
10. Saturation, slope per extra triangle (cycles per ray per SM, N = 1 to 4096, fit with the node term as in F194 where the data allow it, otherwise a slope over N at N >= 256): 0.35 to 0.55 (central 0.43 = 0.67 / 1.56, from the Throughput_6 ratio; the unit gap rate ratio 1.07 to 1.14 would give 0.59 to 0.63): 40 percent; between 0.35 and 0.65: 60 percent; at or below 0.34 (the whitepaper's 2x or more): 15 percent; above 0.65 (no gain over Ada): 25 percent. Ratio Ada / 5090 central 1.5, range 1.0 to 1.9.
11. The whitepaper's 2x: ratio of the Ada per triangle rate (0.67) to the 5090's per triangle rate between 1.8 and 2.2: 20 percent. The ratio lies between 1.2 and 1.8: 55 percent. The OptiX stack scene intercept at saturation (N = 1) within 50 percent of 14.4 (F186, one triangle, Ada; which includes OptiX raygen overhead): 50 percent.
12. At saturation the 5090 per triangle cost is below its own one warp value divided by 32 times a factor of 1 to 3 (the F194 relation held on Ada: 0.67 against 52 / 32 = 1.6 for lane parallel latency): the saturation to one warp slope ratio is 52 / 0.67 = 78 on Ada; on the 5090 between 80 and 160: 55 percent.

Reading rules written now:
- "In the RT core" (S): ncu warp instructions per candidate under 15 AND flat over N = 16, 64, 256 (as T0, T1 here). "SM resident": above 50 and S / C slope ratio above 0.4. Anything between: not determined, reported as such. If S is hardware, the cost per candidate is stated as cycles per sphere against C at one warp and at saturation in D1 and D1b, and ratio in D2.
- Triangle rate: slope over N by least squares at saturation; reported only when R^2 is above 0.98 for N >= 64, else per N values. Node terms are not separated (the OptiX builder's tree is not known), so "per triangle" means "per stacked triangle in this scene" and carries the node growth: it is an upper bound of the pure triangle term.
- Scoring: a range is held when the measured value is inside it; central values are scored as relative error. One run per cell, no cell repeated after reading it, except a failed run (reported).
- Run rules: nvidia-smi (pc14_gpucheck.sh) before every process, timeout -k 2 30 per run (ncu 120), GPU 0, short launches, stop at the first fault, hang, timeout or wrong result, raw files timestamped, opened with mode x.

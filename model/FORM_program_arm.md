# Program arm: is the Mochi frame 0 excess the program (or the instance level)? Form and predictions fixed BEFORE the run (2026-11-16, triton GPU 1, OptiX only)

Gap (F168, F169, F170): Mochi frames 0 to 4 take about 100 us for 100,000 point queries at 1.0 to 1.08 calls per query and 6.25 nodes per query (replay, F165); the plain lattice launch takes 13 us and a refit tree at that call count also 13 us.

## Two checks read from the source and the patch (before any run)
- The 100 us is the trace launch only. The span of F168 is the global timer from the first raygen start to the last raygen end of one owlLaunch2D (probes in the raygen: patch lines `gt0` before and `gt1` after the trace, atomicMin and atomicMax over the launch; notes/q27/mochi_probe_patches.diff). The refit (owlGroupRefitAccel of the GAS and of the instance group) and the update kernel run before it on the host side and are not inside the span; the host chrono times of Mochi are not used.
- How frame 0's tree is built (hostCode.cu lines 222 to 241, owl/UserGeomGroup): the 100,000 particles are sorted by Morton code (largest code first, priority queue) into the primitive order; ONE custom primitive GAS with the flags OPTIX_BUILD_FLAG_ALLOW_UPDATE only (a nonzero flag argument replaces OWL's default PREFER_FAST_TRACE | ALLOW_COMPACTION; to be confirmed against the dumped GAS, not done here), then an INSTANCE GROUP over it (a second acceleration structure, one instance, identity transform, also ALLOW_UPDATE), and the launch traces against the INSTANCE GROUP (maxInstancingDepth 1, traversableGraphFlags single level instancing; the lattice tests of F169 and F170 traced a single GAS and used ALLOW_SINGLE_GAS). Before frame 0, 200 warmup substeps (update kernel, refit of both, launch) run, then 400 substeps per frame, each one refit of both plus one launch. So the tree at frame 0 is the build plus 200 refits (F166: topology constant on the falling lattice, replay exact).
- The Mochi program differs from the lattice program in: the ray payload is a pointer to a 32 byte Particle copy in the thread's local memory; the intersection program loads the 32 byte hit particle from global memory by primitive index, computes a distance (sqrt), and for overlapping pairs does 6 float atomicAdds; the ray flag DISABLE_CLOSESTHIT; box = centre +- 2 radius (overlapping neighbours: spacing 0.002, box 0.0022 wide, so about 2 exact box hits per query including the particle itself, F165).

## Test (ttu/bench/Load_1/load3.cu, load3_dev.cu)
The real dataset (datasets/100k_particles.txt, Morton order as Mochi sorts it), GAS built with ALLOW_UPDATE only, 100,000 queries (particle i, ray direction (0,0,1), tmax 1e-16, ray flag DISABLE_CLOSESTHIT), span from the raygen timers as F168, median of 20 launches after 2 untimed, per warp calls counted by the leader lane (both programs). 2 x 2 arms: PROG 0 (trivial: box load and point test, no report, no particle load, no payload pointer) or PROG 1 (Mochi's raygen and intersection program, same arithmetic, same atomics, forces into a scratch buffer) times GAS only or instance level (IAS, one identity instance, ALLOW_UPDATE, pipeline flag single level instancing). Smallest launch (32 queries) first, then 100,000; timeout -k 2 30, GPU 1, stop on first fault. Calls per query must be 1.0 to 1.2 (else the geometry is not Mochi's frame 0, reported).

Predictions (written before the run; I expect neither is the whole answer):
- A (trivial, GAS): 12 to 20 us (the F169 and F170 value; the overlapping boxes add a few percent calls).
- B (Mochi program, GAS): 15 to 35 us.
- C (trivial, instance level): A plus 0 to 8 us.
- D (Mochi program, instance level, the full replica): 20 to 55 us, not 100.
Decision rule (set now), on D at 1.0 to 1.2 calls per query: PROGRAM AND INSTANCE LEVEL EXPLAIN THE GAP if D >= 70 us (then the shares are B - A for the program, C - A for the instance level, D - B - C + A for the interaction); RULED OUT if D <= 30 us (then the next candidates are the launch sequence, the 200 warmup refits and whatever the build leaves in the tree (not run), the query positions, the update kernel's cache state between launches); in between: partial, report the shares and stop. Not tuned afterwards. One day box.
Caveats stated now: no refit chain here (the fresh tree stands in for build plus 200 refits; F166 says the topology is constant, F170 says a refit chain on a lattice that does not scramble does not degrade); between launches Mochi runs the update kernel (L2 and L1 state differ from back to back launches); the timer resolution is 1.024 us.

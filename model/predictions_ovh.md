# OptiX per call overhead at saturation: predictions (2026-11-16 night, tethys GPU 1, written BEFORE any run; OptiX only, no TTU code of ours)

Question (F178, F185): OptiX adds about 4,000 cycles per optixTrace call at one warp (1,143 warp instructions in the raygen). Is that hidden at whole GPU load, and does the F185 conclusion (no per call term, no refit) hold?

Program: ttu/bench/Ovh_1 (new). The raygen builds its own ray from the launch index (a hash, no ray or result buffers: memory traffic is only the BVH), traces it nrep times (same ray, repeated calls are warm), and writes one word per warp only if an impossible value appears. Variants (same host): TRACE (optixTrace in a loop of nrep = 1 or 3, nrep = 0 skips the call in the same binary) and EMPTY (a raygen with the same hash and sink and no optixTrace in the code at all). Scenes: tri1 (one triangle, every ray hits) and soup (the 100,000 soup, random rays, tmax unlimited). Launch sizes N = 32 (1 warp), 4,096 (1 warp per SM), 16,384, 65,536, 262,144, 1,048,576, 4,194,304, 8,388,608 rays (1D). Per size: 20 timed launches (events, median) and clock calibration launches (lane 0 of each warp: clock64 and globaltimer at start and end: SM clock under load, and the warp latency distribution).
Units: c = cycles per ray per SM = time x f(measured) x 128 SMs / N. d1 = c(TRACE, nrep 1) - c(EMPTY). d3 = (c(nrep 3) - c(nrep 1)) / 2 = cost of one more warm call. Harness reference for the unit alone on the same GPU (F176, Throughput_1, one triangle query, saturated 20 to 32 warps): 0.14 rays per cycle per SM = 7.1 cycles per ray per SM (0.09 at 20 warps, the ramp).

Predictions:
1. One warp (N = 32), tri1, warp latency by the calibration clocks: nrep 1 cold 6,000 to 7,500 cycles (F178: 6,856); one more warm call (nrep 3 minus 1, halved) 4,300 to 5,100 (F178: 4,750); EMPTY raygen under 400 cycles.
2. Warp latency stays within 20 percent of the one warp value up to 4 warps per SM (N = 16,384) and rises roughly in proportion to warps per SM only after the knee. The time per ray stops falling (within 10 percent of its final value) between 16 and 32 warps per SM (N = 65,536 to 262,144), because 6,856 cycles of latency over about 290 issue cycles per warp needs about 24 warps in flight.
3. Saturated (N = 4,194,304 and 8,388,608), tri1, nrep 1: c = 10 to 16 cycles per ray per SM (central 12): the issue bound of 1,143 instructions per 32 rays on 4 schedulers is 8.9, the unit alone 7.1, so the two overlap only partly. EMPTY at saturation under 1.5 cycles per ray per SM.
4. One more warm call at saturation (d3, tri1): 7 to 12 cycles per ray per SM, about the issue bound, i.e. NOT hidden on a trivial scene (d3 at least 1.0 times the unit's 7.1). ncu: warp instructions per warp of the TRACE kernel at nrep 1: 900 to 1,300; per extra call 300 to 700 (the first call carries the setup, so less than the 1,143 for each extra call).
5. soup, saturated, nrep 1: c = 130 to 190 cycles per ray per SM (F182: 0.508 ns per ray unlimited, which is about 175 at 2.7 GHz including its own ray loads); the exposed overhead share o / c below 10 percent (o = the tri1 value of item 3 minus 7.1). I.e. on rays that walk a real tree the per call overhead is hidden behind the unit.
6. SM clock under load: 2.5 to 3.1 GHz, the same for EMPTY and TRACE within 5 percent (not assumed in the units: measured).

Reading rule (written now):
- o_sat = c(tri1, nrep 1, saturated) - 7.1 (cycles per ray per SM, exposed overhead on a trivial scene).
- o_sat <= 9: the overhead is hidden up to the issue bound or better; F185's assumed 9 to 28 range holds at its lower end. 9 < o_sat <= 28: inside the F185 range; no change to the F185 conclusion (adding it worsens F113, no refit) at the measured value. o_sat > 28: F185 conclusion must be redone with the measured value (the term would then be larger than assumed, and a refit of the fixed part becomes the question).
- "Hidden at saturation" for a scene: o_sat / c(scene, nrep 1, saturated) < 0.10. tri1 is expected NOT hidden (item 4), soup hidden (item 5).
- The one warp number is only reproduced if prediction 1 holds within its range; the per call overhead at each load is the series d3(N) and d1(N) reported with the warp latency.

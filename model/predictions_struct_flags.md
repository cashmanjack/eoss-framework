# Build flags and compaction: predictions (2026-11-17, tethys RTX 4090 GPU 1, written BEFORE any timed or counted Struct_1 run)

Question: do PREFER_FAST_TRACE, PREFER_FAST_BUILD, ALLOW_UPDATE and ALLOW_COMPACTION (with optixAccelCompact) change the BVH (size, node count, triangle references) and the traversal cost on the same scene and rays?

Disclosure: the code smoke test (20,000 triangles, 4,096 rays, one launch each, no timing read) printed buffer sizes, which I saw before writing this: none 1,305,600 B; fast trace + compaction buffer 1,403,904 B, compacted 1,196,032 B; header node counts 1,422 (none) and 1,649 (fast trace + compaction); header triangle references 23,000 and 25,000 for 20,000 triangles. The predictions below are for the 100,000 and 1,000,000 triangle soups and the custom primitive scene, not these numbers.

Method: ttu/bench/Struct_1 (OptiX only, no TTU code). Scenes: soup 100,000 and 1,000,000 triangles (the Flags_1 generator), random rays tmax unlimited, 262,144 rays, median of 20 launches; custom AABB cloud 100,000 boxes (half width 0.07) with 262,144 point queries (intersection program calls counted). Configurations: bf none / trace / build x upd 0 / 1 x comp 0 / 1 on soup 100,000 (12), bf x comp on soup 1,000,000 and on the custom scene (6 each). Per configuration: buffer bytes (optixAccelComputeMemoryUsage), final bytes (compacted size when compacted), GAS header: +0x08 used size, +0x58 nodes, +0x60 triangle references, leaf slot count (walker on the dump), time per ray, ncu unit L1 requests per ray (sectors minus pipe lsu, as F182) and warp instructions, one warp cold trace cycles (probe 100 launches).

Predictions (reference = bf none, upd 0, comp 0 unless said):
1. Compaction does not change the tree: nodes, triangle references and leaf slots identical, unit requests per ray within 1 percent, time per ray within 3 percent. Final size equals the used size in the header (+0x08) of the uncompacted build within 2 percent, and is 5 to 25 percent below the buffer OptiX asks for (soup 100,000).
2. ALLOW_UPDATE alone: same triangle references, node count within 3 percent, time per ray within 3 percent (F170: update flag alone changes nothing). Buffer size within 10 percent.
3. PREFER_FAST_TRACE against none: triangle references at least as many (more spatial splits, 1.15 to 1.40 per triangle against 1.15), size +5 to +30 percent, time per ray 0.90 to 1.05 of none (not more than 10 percent faster), unit requests per ray within 0.85 to 1.05.
4. PREFER_FAST_BUILD against none: fewer triangle references (1.00 to 1.10 per triangle), size 5 to 25 percent smaller, unit requests per ray +5 to +40 percent, time per ray 1.05 to 1.6 of none on the 100,000 soup, and the time ratio at 1,000,000 triangles at least the 100,000 value (a worse tree costs more when it does not fit the caches; the BVH of the million soup is about 65 MiB, near the 72 MiB L2).
5. Custom primitive scene: fast build raises intersection program calls per query by 5 to 50 percent against none (boxes overlap more); fast trace within 10 percent of none; update and compaction no change (within 2 percent).
6. The one warp cold latency follows the requests per ray (same sign as 3 and 4), the change is at most the relative change of requests plus 10 points.

Reading rules (written now): a prediction is scored held if every number it names falls in its range on every scene it covers; partly held if on some scenes; missed otherwise. No refit, no rerun with changed settings after the numbers are seen; a changed configuration is a new labeled run. Not covered by this test: the real build time (timed with events only as a side note, not scored), other geometry types, refit quality (F170), instance acceleration structure flags.

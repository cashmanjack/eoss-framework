# Instance transforms and two instance levels: predictions (2026-11-17, tethys RTX 4090 GPU 1, written BEFORE any timed or counted Struct_1 instance run)

Question: (a) does a non identity transform on the one instance level cost anything against an identity one? (b) with two instance levels (IAS to IAS to GAS), is the second level done by the RT unit or handed to the SM?

Background used: OptiX makes one identity instance even for a single GAS (F5, F91) and our own sequence ran that instance level with TTUOPEN.DUAL (F139, F195): one instance level plus the GAS fit one unit sequence. F85: OptiX instancing with real transforms is correct against a CPU reference (no timing).

Method: ttu/bench/Struct_1 (OptiX only, no TTU code; no new TTU sequence class, so no TTU run in this item). Soup 100,000 triangles (the Flags_1 generator) and the custom AABB cloud with point queries, bf none. inst: none (single GAS), id1, r90_1 (rotation about z by 90 degrees, maps the cube onto itself, same work), r37_1 (rotation about z by 37 degrees plus a small translation), id2 (two identity levels), r90_2 (outer rotation about z, inner about x, both 90 degrees, cube onto itself). Control: id1 with the pipeline flag ALLOW_ANY (any=1), because two levels need ALLOW_ANY and a different OptiX code path could be the whole effect. 262,144 rays, median of 20 launches, ncu on one launch: unit L1 requests per ray (l1tex sectors minus pipe lsu sectors), SM load sectors per ray (pipe lsu), warp instructions per ray, one warp cold trace cycles (probe, 100 launches), hit fraction and the per ray results (hit, t, primitive, instance id returned).

Predictions:
1. Correct results: id1, id2 and none give the same hit, t and primitive on every ray; r90_1 and r90_2 give hit fraction within 0.01 of id1 (same geometry, rotated cube; per ray hit and t differ because the geometry moved); instance id returned is the outer (last) instance id 7 in every hit of id1, id2, r90_*.
2. Non identity transform, one level: time per ray of r90_1 within 5 percent of id1, warp instructions per ray within 5 percent, unit requests per ray within 5 percent. r37_1 within 10 percent of id1 in time (different ray to box overlap, so the work differs a little). id1 within 5 percent of none. Reason: the instance record holds the matrix and the unit applies it.
3. Pipeline flag control: id1 with ALLOW_ANY within 10 percent of id1 with SINGLE_LEVEL_INSTANCING in time and within 10 percent in warp instructions.
4. Second level: I put 75 percent on the SM doing it. Decision rule written now, applied to id2 against id1: HANDED TO THE SM if warp instructions per ray are at least 1.5 times, SM load sectors per ray rise, and time per ray is at least 1.15 times; HARDWARE if all of warp instructions, SM load sectors and time are within 10 percent; otherwise MIXED / not determined (reported as such). Numeric predictions under the SM hypothesis: warp instructions per ray 1.5 to 5 times id1, time per ray 1.2 to 3 times, one warp cold latency +500 to +3,000 cycles (a restart costs about one fixed query, F35 and F53: 740 warm).
5. r90_2 against id2: time within 15 percent, warp instructions within 25 percent (a software transform adds a few tens of instructions; I do not expect an identity shortcut).
6. Unit requests per ray (RT unit L1 sectors) of id2 within 15 percent of id1 if the outer level is in software (the unit still walks the same GAS); if the second level is in hardware too the number rises by about the instance node reads (2 sectors or fewer).

Reading rules: scored held / partly held / missed per numbered prediction; the answer to (b) is the rule in 4, applied once, not changed after the numbers. If control 3 fails (any=1 differs by more than 10 percent) the effect of a second level is reported as confounded with the pipeline flag and id2 is compared with id1 under ALLOW_ANY. Not covered: many instances per level (only one instance per level here), instance flags, motion, hardware confirmation from the OptiX code or from our own sequence (a non identity matrix through our own sequence would be a new class of TTU run and is not done here).
